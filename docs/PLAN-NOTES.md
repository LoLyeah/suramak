## Decode path — container support & the ffmpeg-sidecar escape hatch (M5, verified)

- Container support is pure-Rust **symphonia**: `isomp4` (mp4/m4a/mov/m4v) and `mkv` (matroska/webm, already active via symphonia's default features — now pinned explicitly) plus the pre-existing readers/codecs. A video file's **first audio track** is decoded; video streams demux as `CODEC_TYPE_NULL` and are skipped. Opus demuxes (mkv/webm) but symphonia 0.5.5 ships **no Opus decoder** — it fails with the actionable `UnsupportedFormat` message (`… convert it first, for example: ffmpeg -i "clip.webm" "clip.mp4"`).

## AppKit window material — the float-glass layering rule (verified, M8.5)

Where these conflict with a tempting "simplification", this wins; the arrangement survived two crashes.

- **The window's `contentView` stays the base material's container.** On macOS 26+ the base `NSGlassEffectView` is the content view and the render surface lives inside its `contentView` property (in M8.5 that property is a plain `NSView` container); pre-26 the `NSVisualEffectView` is the content view with winit's view as a subview. Content placed as an arbitrary sibling above the glass is not supported and aborted with `AppKit/NSGlassEffectView.swift:736: Fatal error` once the window ran modal machinery (the import open panel, macOS 27, 2026-10-13 — commit `ed1fee1`). `NSGlassEffectView.h` only guarantees z-order for the `contentView` property.
- **The floating record control's glass (M8.5) is an ordered subview between the base material and the winit view** — inside the plain container that is the base glass's `contentView`, ordered directly below the render surface (`addSubview:positioned:relativeTo:`). It is **never** made a `contentView`, and it is never added as an arbitrary subview of a glass view.
- The float glass is created lazily (first `set_float_rect(Some(..))`), hidden on `None`, and re-positioned on every resize; its frame is set in the host's coordinate space (flipped-aware), so the same top-left-origin `suramak_glass::float_rect` drives both the egui painter and AppKit.
- On machines without the `NSGlassEffectView` class (macOS < 26) there is no float glass — `set_float_rect` is a clean no-op and the UI paints its fallback pill (same rect, same behavior).

## Multi-source capture — drift approach & per-app selection (M6, verified)

- **One recording = N sources mixed offline at Stop.** Each selected input gets its own cpal session (`MultiRecorder`, one `Recorder` per input, started together, stopped together); at Stop the pure mixer (`suramak-asr::mix`, compiled everywhere — no feature gate) stages every buffer to 16 kHz with the *same* `resample_16k` the solo path uses, applies per-source gain/mute, sums, and the existing `write_recording_wav` writes the one 16 kHz mono i16 WAV. The live meter shows the loudest source (a true post-mix meter would need the mix); gain/mute apply to the whole recording (they are applied at finalize — deliberate, documented).
- **Clock-drift approach: measured-rate alignment, not sample insertion/deletion.** Device clocks differ by tens-to-hundreds of ppm, so N sources recorded over the same wall-clock session deliver *different sample counts* for the same span. The mixer measures each source's effective rate from the two exact quantities the capture layer knows — samples delivered `N` and the session span `D` (runtime `Instant`) — and resamples that source at `ρ = N/(rate·D)` via a constant-ratio Catmull-Rom stretch (stage 2) on top of the standard 16 kHz stage 1. Alignment error is therefore bounded by the *measurement* error of `D` (a few ms of `Instant` noise, independent of run length) — never by run length. Because the correction is a constant ratio, there is no correction *event* to hear: nothing is ever inserted or dropped, so it cannot click (`never_clicks` test: max sample-to-sample step in the steady region equals the sine's own slope, 0.17257). `ρ` is clamped to ±2% (beyond that the measurement is not trusted — stalled device, bogus duration — and the clamp is reported).
- **Numbers (unit tests, `cargo test -p suramak-asr`)** — a 24 kHz source clocked ±250 ppm over a 3-minute session: naive (nominal-rate) mixing slides its pulse markers by ±35 ms at t=160 s; the corrected mix stays within 1 sample (0.00 ms) at every checkpoint. Two sources at ±300 ppm over 100 s: naive slides them apart by 36 ms; corrected, both stay at 0.00 ms. Exact outputs in `docs/reports/M6.md`.
- **Solo regression guard**: one source + unity gain + a session whose measured clock equals nominal → output is *bit-identical* to the pre-M6 path (`mix::tests::unity_solo_matches_the_existing_single_source_path`), except that the FFT resampler's tail zero-padding is trimmed to the session length. A solo source whose measured clock deviates gets the (sub-ppm-scale) ratio correction — same format, length semantics and level policy.
- **Clipping policy**: per-source gain applies *before* the sum; the sum is never squashed (no limiter/AGC). Hard saturation happens only where 16-bit PCM requires it — `write_wav_i16` clamps to ±1.0 full scale — and the mixer *counts and reports* every saturated sample (`clipped_samples`, `peak`), so clipping is visible, never silent.
- **Per-app selection**: settings store **process keys** — the bundle id (`us.zoom.xos`) when the process has one, else `pid:<pid>` — and resolve them to *live* pids at record time through the HAL process-object list (`kAudioHardwarePropertyProcessObjectList`). A key with no running process fails the start with an actionable message; it is never widened to full system audio. The tap itself is `CATapDescription`'s `-initStereoMixdownOfProcesses:` (`ProcessSelection::Only`), a stereo mixdown of exactly those processes; the per-app aggregate device is named `Suramak App Audio` (distinct from `Suramak System Audio`, so both taps can run at once). Suramak's own process is excluded from the picker (a tap must never capture itself).
- **macOS-only surface**: the process listing and both tap initializers can only be exercised on macOS 14.2+ (owner smoke, USER_SMOKE item 17); from Linux, `cargo check -p suramak-taps --target aarch64-apple-darwin` compile-checks the whole darwin path (pure Rust, no SDK needed).

## Live transcription — windowing, backlog policy & the final-pass rule (M7)

- **Cadence + overlap**: the live stream is windowed every **4 s** of new audio with **1.5 s of context overlap** carried into the next window's head (`LiveConfig`, bounds enforced: cadence 4–6 s, overlap 1–2 s). A window's samples cover exactly `[window_start − overlap, boundary)`; the very first window is clamped at the session start. Words spoken across a boundary therefore decode with their context; the merge drops decoded segments that end within **50 ms** of the already-covered frontier (whisper timestamps are centiseconds — that tolerance is below any word), so the overlap re-decode never duplicates text. The last `< step` of audio is deliberately left to the final pass.
- **Backlog policy (never starve capture)**: the per-frame feed only *reads* the already-captured buffers (a per-source read cursor; the accumulated buffers and the final WAV are untouched) and appends to the pure scheduler; decoding runs on its own thread (`suramak-live-decode`) behind a **bounded queue with drop-oldest** (`max_queued`, default 2 — the newest audio is what the provisional view needs). The **skip-and-merge guard**: when a window closes while the previous decode is still running, the window is **skipped** (per-session count, logged at every change and surfaced in the record view as `N window(s) skipped to keep up — live updates may lag; the final pass is unaffected`) and its span **merges into the next window** — no audio is ever lost from the live transcript, only the cadence degrades. Slower machines lag live updates; the final pass is unaffected (the workorder's accepted trade-off).
- **One stream, one path**: the live feed is the same 16 kHz stream the recording consumes — the runtime flushes each source's new device-rate samples (≥ 1 s per source, all sources together to stay time-aligned) through the **same `mix::mix`** engine the final pass uses, per-source gain/mute from the record view. Chunk-wise and session-less, so **no clock-drift correction** on the live stream (provisional only); the final recording remains the one full-session drift-corrected mix. Decode rides the existing whisper machinery (`whisper::transcribe` + `ContextCache`, same model / language / initial prompt / engine plan), one window at a time, on a context of its own (lazily loaded on the first window — a second model context lives only while the recording runs; documented trade-off).
- **The final-pass rule (hard)**: the provisional list is display-only and is cleared the moment Stop is pressed; the final pass is exactly today's `pipeline::transcribe_file` over the unchanged recording WAV (`pipeline.rs` / `whisper.rs` / `worker.rs` have **zero diffs** in M7), so for the same input the artifact is byte-identical. The Linux tiny-model e2e pins it: the final pass runs before and after a full live session and every segment (idx/timestamps/text) must match.
- **Known limit (provisional-only)**: a phrase spoken across a window boundary can briefly appear twice in the provisional list (whisper re-decodes the boundary with the overlap context and may re-segment it differently); the exact-overlap duplicates are dropped by the 50 ms rule, and the final pass replaces the whole list — this can never reach a saved transcript.

## Known non-issues (verified — do not chase)

- **macOS 27 + winit 0.30.13 IME** — two latent crashes, both first-hit on the owner's Mac (2026-10-13): (1) `-[NSView inputContext]` is nil on macOS 27, so the first text-field focus panicked (`set_ime_cursor_area` → `.expect("input context")`, view.rs:901) — fixed by the `LoLyeah/winit@63f21f8` fork pin (nil-tolerant guards; drop the pin when upstream handles nil). (2) `set_ime_allowed(false)` (text field loses focus) SIGSEGVs in `objc_release` releasing the marked-text cell — released object is the literal `0x3` (crash `48A5EFA3-…`); root cause not yet pinned. Workaround shipped: on macOS the shell forces `platform_output.ime = None` every frame (`shell.rs`), so egui-winit never calls `set_ime_allowed` at all; en/id typing is unaffected (no IME needed). Revisit the winit 0.31 IME rework before re-enabling IME.
- Build-end warning *"block v0.1.6 … code that will be rejected by a future version of Rust"*: the frozen `block 0.1.6` comes from the **`metal` crate inside wgpu/wgpu-hal** (our renderer), not from the audio stack; the flagged construct is `static _NSConcreteStackBlock: Class;` (uninhabited static, rust-lang/rust#74840). Harmless today; disappears when wgpu/metal migrate to `block2`/objc2 upstream. Do not vendor or patch it pre-1.0.
- **macOS 27 SDK**: the CoreAudio aggregate-device description keys (`kAudioAggregateDeviceUIDKey`, `…NameKey`, `…IsPrivateKey`, `…TapListKey`, `kAudioSubTapUIDKey`) are **string-literal macros** with no linkable symbols and no `dlsym` hits; `suramak-taps` builds the dictionary keys as CFStrings from the literal values (`"uid"`, `"name"`, `"private"`, `"taps"`, `"uid"` — from the SDK header). Keep the literal-CFString approach if a future SDK shifts again: the HAL matches dictionary keys by string content.
- On macOS 27 machines `ld` prints *"object file … was built for newer 'macOS' version (27.0) than being linked (11.0)"* for C deps: benign deployment-target noise (rustc's default `-mmacosx-version-min=11.0` vs SDK-built objects); the app's real minimum is `LSMinimumSystemVersion` in `Info.plist`.
