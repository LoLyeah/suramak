## What was implemented

### 1. The mixing engine — pure, Linux-testable (`crates/suramak-asr/src/mix.rs`, NEW)

**Architecture rule honoured**: the whole mixing/resampling/drift DSP lives in a module that compiles on **every** platform (no `capture` feature, no cpal, no device); only device I/O stays macOS-gated in `capture.rs`. `mix::mix()` consumes per-source mono f32 buffers + the session span and returns the one 16 kHz mono f32 stream; `mix::mix_to_wav()` runs the existing `write_recording_wav` (16 kHz mono i16 — the single recording format, unchanged).

- **Per-source gain before the sum; mute = gain 0.** The sum is **not** squashed.
- **Clipping policy (documented, never silent)**: hard saturation happens exactly where 16-bit PCM requires it (`write_wav_i16` clamps to ±1.0 full scale — the pre-existing behavior); the mixer counts every saturated sample and reports the pre-saturation peak (`clipped_samples`, `peak`). No limiter, no automatic gain reduction.
- **Solo regression guard**: one source + unity gain + measured clock == nominal → **bit-identical** to the pre-M6 path (`mix` stage 1 *is* `capture::resample_16k`, the same function the solo path always used; the no-correction branch is an exact pass-through). The one deliberate difference: with a session, the FFT resampler's tail zero padding is trimmed to the session length.

### 2. Clock-drift handling (the documented approach)

Device clocks differ (tens-to-hundreds of ppm), so N sources recorded over the same wall-clock session deliver *different sample counts* for the same span; mixing at nominal rates slides the fast source ahead by `ppm · t` (45 ms after 3 min at 250 ppm — and growing).

**Approach: measured-rate alignment, not sample insertion/deletion.** The mixer measures each source's effective rate from the two exact quantities the capture layer knows — samples delivered `N` and the session's wall-clock span `D` (the runtime measures it around the live streams with `Instant`) — and resamples that source at its measured rate instead of the nominal one:

```
ρ = N / (rate · D)        (measured rate / nominal rate; clamped to ±2%)
```

- **Stage 1**: the source is resampled to 16 kHz exactly as today (`resample_16k` → core's rubato FFT resampler).
- **Stage 2**: the 16 kHz stream is stretched by `ρ` with a **constant-ratio 4-point Catmull-Rom** fractional resampler.

Why this **never clicks**: the correction is a constant resampling ratio — no sample is ever inserted or dropped, so there is no correction *event* to hear; the interpolator is the exact identity at integer positions (`t == 0 → p1`). Why alignment is **bounded**: the residual error is the *measurement* error of `D` (a few ms of `Instant` noise) plus a constant startup offset — independent of run length, unlike the naive `ppm · t`. `ρ` is clamped to ±2% (beyond that the measurement is not trusted — stalled device, bogus duration — and the clamp is reported per source). The per-source report (`measured_rate`, `drift_ppm`, `clamped`, `applied_gain`, `muted`) is logged by the runtime at Stop.

**Synthetic alignment proof (exact numbers in acceptance §6)**: 3-minute runs, ±250 ppm (24 kHz), ±300 ppm two-source (16 kHz), 100 s: naive mixing moves the pulse markers by up to ±35 ms (analytical `ppm·t` matched to ≤ 4 samples); the corrected mix stays at **0.00 ms** (within 1 sample) at every checkpoint. The click test measures the max sample-to-sample step in the steady region: **0.17257 = the 440 Hz sine's own slope at 16 kHz** (2·sin(π·440/16000)); the only larger steps are the FFT resampler's warm-up (~first 90 samples) and tail truncation (~last 2 ms) — pre-existing properties of the single-source path, measured and printed for honesty.

### 3. Multi-source capture (`crates/suramak-asr/src/capture.rs`)

- `CaptureInput { Default | Device(name) | SystemAudio | AppAudio(pids) }` — the settings list maps onto it; `From<&AudioSource>` keeps the M3 path intact.
- `MultiRecorder`: one `Recorder` per input, started together (`start_recording_multi`; the first failure tears the already-started sessions down — never a half-open session), `stop()` returns every buffer + the session span. Live meter = the **loudest source's** rolling RMS (a true post-mix meter would need the mix, which happens at Stop; the workorder allows the single combined meter).
- `list_audio_processes()` (feature-gated; macOS impl in `suramak-taps`) + pure `resolve_app_processes(keys, processes)` — unit-tested on Linux.
- The macOS path (tap creation, aggregate-device matching by name) is unchanged; the per-app tap gets a distinct aggregate name (`Suramak App Audio`) so system-audio and per-app taps can run at once.

### 4. Per-app capture (`crates/suramak-taps`, additive only)

- `ProcessSelection::Only(Vec<u32>)` → `-initStereoMixdownOfProcesses:` (a stereo mixdown of exactly those processes; verified against CATapDescription's documented initializers; the process-object translation is the same one `AllExcept` already used).
- `TapConfig::app_audio(pids)` + `APP_TAP_DEVICE_NAME`; `AudioProcessInfo` + `settings_key()`; `list_audio_processes()` via `kAudioHardwarePropertyProcessObjectList` (`0x70727323`) reading `kAudioProcessPropertyPID` (`'ppid'`), `…BundleID` (`'pbid'`), `…IsRunningInput` (`'piri'`), `…IsRunningOutput` (`'piro'`) — all fourccs verbatim from the SDK-generated `objc2-core-audio` bindings; Suramak's own pid is excluded. Existing tests untouched and green (2 → 5).
- Settings store **keys** (bundle id, else `pid:<pid>`); the runtime resolves them to *live* pids at record time — a key with no running process fails with `no running audio process matches '…' — start the app (and play audio), refresh the list, and retry`, never a silent widening.

### 5. Settings (additive field) + UI

- `suramak-core`: `RecordSource { Default | Device | SystemAudio | AppAudio { apps } }` + `RecordingSettings.sources: Vec<RecordSource>` (`#[serde(default)]`); `effective_sources()` falls back to the legacy `audio_source` when the list is absent. Persisted as `[[recording.sources]]` tables; `audio_source` follows the first entry on save (older readers keep a sane view; `AppAudio` degrades to full `SystemAudio` for them — documented).
- `settings_form` (egui-free, unit-tested): checkbox-list logic (`set_checked`, `set_app_audio_checked`, `set_app_checked`, canonical ordering), **never-zero validation** (`sources_problem()`: ≥1 source; the app entry needs ≥1 app — Save refuses, the previous list stays), `apply` syncs the legacy field.
- `settings.rs` view: the dropdown became the **checkbox list** (Default microphone, every enumerated device, System audio, "Only an app…" with the inline running-audio-process picker + Refresh); capture-less builds render it read-only with the existing copy; macOS-only entries hidden elsewhere (Addendum A behavior preserved).
- `record.rs`: a `sources` card — one row per live source (label, mute, gain slider 0–2×). Gain/mute are applied by the mixer at finalize (documented: they apply to the whole recording).
- `runtime.rs`: `Effect::StartCapture` resolves the list (per-app keys → pids), opens `MultiRecorder`, reports labels; `StopCapture` stops everything, mixes with the view's gains/mutes + the measured span, logs the per-source report, writes the wav through the unchanged pipeline; new `Effect::RefreshAudioProcesses`.

## Deviations from the WORKORDER (with reasons)

1. **The old dropdown's key codec was removed** (`settings_form::audio_source_key`/`audio_source_from_key` + its test): the checkbox list stores `RecordSource` values directly, so the codec had no remaining caller (it would have been dead code in a bin crate). The new settings-level round-trip tests cover the persisted shape. Likewise `AppState::record_device` was replaced by `record_sources` (the runtime reports the full source list); the existing recording test was updated accordingly. No behavior lost.
2. **Gain/mute apply to the whole recording** (the mix is computed at Stop from the captured per-source buffers). The workorder asks for "at least gain/mute per source at record time"; a piecewise gain timeline was not built (documented instead of silently surprising). The controls are disabled once Stop is pressed.
3. **The live meter shows the loudest source** — post-mix metering would require the mix, which is a Stop-time computation; the workorder explicitly allows the single combined meter.
4. **The long drift tests run at 24 kHz / 16 kHz** (3-minute and 100 s synthetic sessions) to keep the suite fast (~18 s for the whole mix module, all non-ignored). The 48 kHz FFT stage-1 path is exercised by the solo/format/clipping tests and the demo; drift is rate-agnostic (it is measured in seconds, not samples).
5. **The `capture` feature compiles and tests on this Linux VPS** (ALSA happens to be present): `cargo clippy -p suramak-asr --features capture-test --all-targets -- -D warnings` and `cargo test -p suramak-asr --features capture-test --lib` (38 passed; includes the enumeration smoke test) are recorded as extra evidence. The *darwin* cross-check of `suramak-asr` itself still fails inside `ring`'s C build (pre-existing class, documented in M5 §deviation 6) — so the macOS device path is covered by the macOS CI build + owner smoke, stated as such below.
6. **The FFT resampler's edge behavior is out of scope**: its first ~90 output samples are numerical warm-up and its tail truncates ~2 ms of content (both pre-existing on the solo path; the truncated tail is zero-padded to the session length by the mixer). The never-clicks assertion therefore measures the steady region and *prints* the edge maxima (0.18080 head / 0.20642 tail) so nothing is hidden.
7. **Reset-to-defaults** restores the source list to `[Default]` in the form only (Save persists) — the existing reset semantics, unchanged.
8. **Solo + measured session**: output length is `round(D·16 kHz)` instead of the resampler-padded length — up to ~21 ms shorter at the tail (padding trim). Format, level policy and the audible content are identical; the bit-identity test pins the no-session case exactly and the prefix equality for an exact measured clock.
