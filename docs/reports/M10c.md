## What was implemented

### 1. The decoder, in the single decode path (`suramak-core`)

**Dependency** (workspace `Cargo.toml` → `crates/suramak-core/Cargo.toml`):
`symphonia-adapter-libopus = "0.2"` — cargo resolved **0.2.9** (checksum
`2bfc8e95…`; the 0.3.x line targets symphonia 0.6 and was deliberately not
taken), pulling **`opusic-sys 0.7.5`**, whose `bundled` feature (the adapter's
default) compiles **libopus 1.6.1** from the crate's vendored source via cmake
+ cc into the binary. `Cargo.lock` gains exactly those two packages.

**Registration** (`crates/suramak-core/src/decode.rs`): the decode path now
builds its own codec registry —

```rust
fn codec_registry() -> &'static CodecRegistry {
    static REGISTRY: LazyLock<CodecRegistry> = LazyLock::new(|| {
        let mut registry = CodecRegistry::new();
        symphonia::default::register_enabled_codecs(&mut registry);
        registry.register_all::<OpusDecoder>();
        registry
    });
    &REGISTRY
}
```

— and `decode_stream` calls `codec_registry().make(...)` where it previously
called `symphonia::default::get_codecs().make(...)`. The default registry is a
`lazy_static` that cannot be extended (verified in the symphonia 0.5.5 source:
`src/lib.rs` — `CODEC_REGISTRY` is built by `register_enabled_codecs` into a
private static), so the registry is rebuilt once per process with the default
set **plus** the adapter's `OpusDecoder` (the exact 0.2.x call from the
adapter's README). `symphonia`'s `opus` feature was **not** enabled — verified
it does not exist in 0.5.5 at all (no `opus` entry in the crate's feature
table; the upstream name is a no-op placeholder), so there is nothing to
double-enable.

`error.rs` is **unchanged**: the actionable recipe (`cannot decode … — convert
it first, for example: ffmpeg -i …`) still fires for a genuinely unsupported
codec (ALAC-in-m4a is the live case now) and for unknown containers; webm/mkv/
Ogg-Opus can no longer reach it.

## Deviations from the WORKORDER (with reasons)

1. **A new ALAC fixture** carries the negative recipe test. The workorder says
   “keep a negative recipe test on a genuinely unsupported codec” — the two
   previous negatives *were* the opus files (now positive), so a real
   unsupported-codec file was needed. ALAC-in-m4a is the honest analog: the
   `isomp4` reader demuxes it (codec params filled from the `alac` atom) and
   this build has no ALAC decoder (the `alac` feature is off), so it exercises
   the exact `make() → Unsupported` branch the opus tests used to pin. It is
   lossless, hence 284 KB (larger than M5's ≤100 KB set).
2. **The webm/mkv opus fixtures decode at 16 kHz, not 48 kHz.** ffmpeg wrote
   `SamplingFrequency = 16000` into the Matroska audio element (parsed out of
   the file bytes to confirm: both fixtures, no `OutputSamplingFrequency`), the
   mkv reader uses that field, and libopus's decoder accepts 8/12/16/24/48 kHz
   output rates — so the adapter decodes at the container's declared rate. A
   raw Ogg-Opus file declares 48 kHz per the Ogg-Opus mapping. Both are
   correct; the pipeline resamples to 16 kHz either way. The tests assert each
   container's declared rate (16 kHz for webm/mkv, 48 kHz for `.opus`) and the
   e2e proves the content (the transcript matches).
3. **Docs/copy beyond the workorder's list**: `README.md`, `CHANGELOG.md`
   ([Unreleased]), `PRODUCT.md` (status line on the M10C bullet + a
   “superseded for Opus” pointer on the M5 bullet) and the CLI help string all
   carried now-false claims (“WebM/Opus fails with a conversion hint”). Same
   precedent as M5 (its report's deviation 4/5). `docs/reports/M5.md` is
   historical and untouched.
4. **The home drop-zone caption** (`wav · mp3 · m4a · flac · ogg · mp4 · mov ·
   m4v · mkv — transcribed on this machine…`) was **not** extended, per “no
   other UI change”: it is a curated list that already omits `aiff`, and the
   picker is the acceptance-relevant surface. Flagged for a follow-up copy pass
   if the owner wants the caption to name webm/opus.
5. **MSRV note**: the adapter declares `rust-version = 1.89`, the workspace
   declares 1.85. Cargo (resolver v2) selects it regardless and the toolchain
   is 1.99, so builds are unaffected — but the workspace's declared MSRV now
   understates the default build's true floor. The pin was left alone (changing
   it touches every crate's metadata) and is recorded here as an honest
   boundary.
6. **The e2e lives in `suramak-asr/tests/pipeline.rs`** (ignored, release-only,
   tiny model) — the workorder said “mirror it as a test if cheap”; that is the
   file where every whisper e2e already lives, and it re-uses the existing
   model-skip/`SURAMAK_REQUIRE_MODEL` gating.
