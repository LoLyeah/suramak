## What was implemented

### 1. F1 — Custom language codes (Settings)

`SettingsForm.language` stayed a `String` (no data-model change); the selector stopped constraining input.

| Piece | Summary |
|---|---|
| `LANGUAGES` + `CUSTOM_LANGUAGE_LABEL` | The three presets (`auto`, `en`, `id`) stay; `"Custom…"` is a fourth entry. |
| `normalize_language_code(raw)` | Loose validation: trim; 2–8 chars of ASCII letters/digits/`-`; returned lowercased. `Err` carries the inline hint (`'e!' is not a usable language code — use 2–8 letters, digits or '-' (e.g. es, jv)`; empty → `enter a language code (2–8 letters, digits or '-')`). |
| `SettingsForm.language_custom` / `language_draft` | UI-only fields: Custom… selected + the free-text draft. `from_settings` marks any non-preset code (e.g. `fr` from an older file) as Custom… with the code seeded in the field. |
| `validated_language()` | The value `apply` persists: preset as-is, or the validated custom code. |
| `apply()` | Persists the language **only when it validates** — an invalid draft is refused and the previous `settings.asr.language` stays (everything else still saves). |
| `language_hint()` | The caption under the field: `custom: <code> — not officially supported; the model may produce poor results` (grey), the neutral "type a code …" prompt while the draft is empty, or the red validation hint. |
| View (`app/settings.rs`) | Presets + `Custom…` chips; choosing Custom… reveals a small text field (`es, jv…` hint) and the caption row below. Clicking a preset deselects Custom…; switching to Custom… seeds the field from a previous non-preset code. |
| Tests (egui-free, `settings_form.rs`) | custom accepted + lowered + toml round-trip; validation bounds (2/8 chars, dash, case, rejects empty/1/9/`!`/space/non-ASCII/`_`); invalid refuses + keeps the previous value; presets still win over a stale draft; the older-file `fr` case now asserts Custom… + seeded draft. |

The worker plumbing (`settings.language` → `Job.lang`) is unchanged; the end-to-end run below shows a transcript transcribed with the custom code recorded as `es` in its metadata.

### 2. F2 — Trash button (delete a transcript)

- **`Effect::DeleteTranscript { id: Uuid }`** (`app/mod.rs`, next to `Effect::DeleteModel`, same doc style).
- **State**: `AppState::delete_open_transcript()` emits it for the open editor; `AppState::on_transcript_deleted(id, result)` sets `deleted <title>` (title from the open editor, else the library row, else the id) and returns `Effect::RefreshLibrary` on success; when the deleted transcript was the open one it closes the editor, clears the polish review/undo and navigates Home (matching `open_editor`'s rule). Errors → `could not delete <title>: <err>` in the status line and no state change. Nothing panics.
- **Runtime** (`runtime.rs`): arm mirroring `DeleteModel` → `Runtime::delete_transcript(id)` → `store.delete_transcript` → `state.on_transcript_deleted`. Missing store → "library database unavailable" through the same status mechanism.
- **UI** (`app/editor.rs`): a discreet clickable glyph (🗑) in the editor header left of `Home`; arming it swaps in the in-place confirm `Delete? ✔ ✖` (cancel disarms, confirm emits the effect). State: `Editor.confirm_delete` (UI-only, reset by `Editor::open`).
- **Sidebar**: disappears via the `RefreshLibrary` round-trip (`on_library_loaded` drops the stale selection).
- **Store test** (`crates/suramak-core/src/store.rs`): direct-table unit test — deletes one transcript, asserts **0 segment rows remain for it** and that a **second transcript keeps its header + both segments**, that `get_transcript`/`list_transcripts` reflect it, and that re-deleting reports not-found. (No pragma fix was needed: the bundled SQLite is built with `SQLITE_DEFAULT_FOREIGN_KEYS=1` — `libsqlite3-sys-0.30.1/build.rs:123` — so the schema's `ON DELETE CASCADE` is genuinely enforced; this test is the proof the workorder asked for.)

## Deviations from the WORKORDER (with reasons)

1. **Confirm glyphs** — the workorder's example `✓ ✕` (U+2713/U+2715) are **not in egui's bundled fonts** (checked the cmap of `epaint_default_fonts-0.33.3`'s NotoEmoji/emoji-icon-font/Hack/Ubuntu: absent). The available equivalents are used instead: **🗑 (U+1F5D1, emoji-icon-font), ✔ (U+2714) and ✖ (U+2716)**. This is the example's intent, and the glyphs are confirmed rendering in the E2E screenshots below.
2. **`uuid` added to `crates/suramak-ui/Cargo.toml`** — required to name `Uuid` in `Effect::DeleteTranscript { id: Uuid }` (the workorder's exact signature). `Cargo.lock` gains one dependency edge for `suramak-ui`; **no new resolved crates** (uuid was already in the graph via core/cli).
3. **Empty custom draft is a neutral (grey) prompt, not a red error**, but it still refuses to persist like any invalid value. Invalid non-empty input gets the red hint.
4. **Save with an invalid draft persists everything else** and keeps the previous language (the workorder says "refuse to persist that value (keep the previous selection)"); the status line still reports `settings saved …` and the red hint stays visible next to the field.
5. **The trash/confirm state lives on `Editor`** (`confirm_delete: bool`), which is the module's existing UI-state struct — no on-disk format change; settings.toml and the DB schema are untouched.
6. **The CLI's own message** `saved to library: id <uuid>` (`crates/suramak-cli/src/cmd/transcribe.rs:189`) was left as-is: the out-of-band request was scoped to the Home status line and to files already being touched, and that file is not one of them.
7. **`cargo fmt` was run once** to normalize three rustfmt diffs in the new code before the acceptance block; `cargo fmt --check` is clean.
8. **Language-chip click polish (small, inside the same view change)**: clicking the already-selected chip is now a no-op (it no longer flags the form dirty); a genuine chip change still marks it. Note for context: the "unsaved changes — press Save" caption is composed from a **per-frame** `dirty` flag (pre-existing M3 behavior) — it is a one-frame flash, not a persistent indicator, so it is not screenshot-stable; the persisted `SettingsForm.dirty` field is unchanged. Verified in the running app that a chip change updates the form (Custom… → auto) and re-clicking the selected chip does not.
