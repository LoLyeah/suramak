## What was implemented

### The spike: `sparkle-updater` 0.1.0 (the crate), not a hand-rolled binding

`docs/WORKORDER-M12.md` asked for a spike between the published crate and a minimal own objc2 binding to `SPUStandardUpdaterController`, preferring the crate "unless it blocks". The crate covers exactly the subset the workorder names — start/stop, event callbacks, gentle reminders, the relaunch hook, the automatic-check preference, `canCheckForUpdates`, `checkForUpdates`, `currentVersion`, `feedURL` — as objc2 bindings for **Sparkle 2.9.6** with no Tauri/GPUI/Tokio dependency (its root plugin is an adapter *over* it). What it deliberately does **not** wrap (its README says the low-level bindings stay private) is the app-menu item — that is the one piece of own objc2 code here. A hand-rolled binding would have had to re-create the whole surface plus the delegate trampolines; the crate is the smaller, reviewed path. **Decision: the crate.**

Facts pinned from the crate's published sources (all of them exercised by the darwin probe below):

- `SparkleUpdater::new(mtm, UpdaterConfig{event_callback, relaunch_handler, gentle_reminders}) -> Result<Option<Self>>`; `Ok(None)` when the executable is not inside a valid `.app` bundle (bundle path must end in `.app` and the bundle id must be non-empty); `Err(SparkleInit)` when Sparkle refuses the configuration; `new` installs callbacks *before* starting.
- `EventCallback = Rc<dyn Fn(UpdateEvent)>`, `RelaunchHandler = Rc<dyn Fn(UpdateInfo, RelaunchContinuation)>`, `GentleReminders` is `dyn`-compatible with the observational methods overridden here; `RelaunchContinuation::resume(self, MainThreadMarker)`.
- `UpdateEvent` is `#[non_exhaustive]` (17 variants + `name()`/`payload()`) — the log match has the required wildcard arm.
- The crate's build script needs `SPARKLE_FRAMEWORK_PATH` (a directory containing `Sparkle.framework`) on macOS and emits `-framework Sparkle`; it never downloads, bundles, or signs anything — that is this repo's pipeline (`fetch-sparkle.sh` / `make-app.sh` / `build.rs`).

### `crates/suramak-core`

`UpdatesSettings { auto_check: bool }` (serde default **true**, `Settings.updates` with `#[serde(default)]`) — older settings files load with automatic checks ON, and the TOML round-trip is pinned by tests.

### `packaging/Info.plist`

`SUFeedURL = https://github.com/LoLyeah/suramak/releases/latest/download/appcast.xml` and a clearly-marked placeholder `SUPublicEDKey` (an XML comment above it + the README/report guides + a boot-time warning + a CI warning). The placeholder is **shape-valid on purpose**: base64-decoded it is the ASCII marker `SURAMAK-PLACEHOLDER-ED25519-KEY!` (32 bytes), because Sparkle's configuration check *refuses to start the updater* for an invalid-shaped key (`SUSignatures.m`: `SUPublicKeys` → `SUSigningInputStatusInvalid` → "The EdDSA public key is not valid for …" → `startUpdater` returns NO). With a valid-shaped placeholder the updater starts, checks, and **matches no signature** — the workorder's "the placeholder public key matches nothing" — and the app logs the loud reminder at every boot until the owner sets the real key.

## Deviations from the WORKORDER (with reasons)

1. **`--embed-release-notes` instead of a linked release-notes file.** The
   workorder's parenthetical ("same base name so Sparkle links the notes") is
   satisfied as the *pickup*: `generate_appcast` uses the same-named `.md`
   (source-verified in `ArchiveItem.releaseNotesPath` — `.html` → `.txt` →
   `.md` → `.markdown`). Embedding was chosen because a *link* would be a
   relative URL resolved against `releases/latest/download/` at update time
   (`releaseNoteURL(for:)`: prefix → feed URL → relative) and would require
   attaching the `.md` to every release — the workorder's attach list is
   `appcast.xml` + deltas only, so a linked `.md` would 404. Embedded markdown
   lands as `<description sparkle:format="markdown">` (Sparkle 2.9 renders it,
   macOS 12+). Switching to linked notes later = drop the flag, add
   `--release-notes-url-prefix` and attach the `.md` (already staged in the
   artifact).
2. **`make-app.sh` gained `SURAMAK_FEATURES`, and release.yml's make-app step
   now passes `speech-transcriber,updates`.** make-app.sh builds the UI itself
   (`cargo build --release -p suramak-ui`) — without the env, its build
   *clobbers* the feature-enabled binary from the workflow's earlier step, so
   the shipped app would carry neither feature (a pre-existing latent issue:
   the step's own comment claims SpeechTranscriber is compiled into the
   artifact). Passing the same feature set to the step that actually ships is
   the minimal fix; the first build step is unchanged.
3. **The rpath lives in a new `crates/suramak-ui/build.rs`** as
   `cargo:rustc-link-arg-bins=-Wl,-rpath,@executable_path/../Frameworks`
   (macOS + feature only) rather than an `install_name_tool` post-edit in
   make-app.sh: it is declarative, applies to every build path (CI bounded
   build, release, local), and keeps the packaged script from patching a
   Mach-O. The make-app contract test asserts the script does *not* use
   `install_name_tool`.
4. **The appcast logic lives in `scripts/make-appcast.sh`** (called by the new
   release.yml step). The workorder asked for the step in the macOS job — it is
   there — and the script keeps the semantics testable on Linux (§9) and
   idempotent (the staging dir is rebuilt from scratch; EdDSA is
   deterministic).
5. **The placeholder `SUPublicEDKey` is shape-valid** (32 bytes decoding to the
   ASCII marker). Reason: an invalid-shaped value makes Sparkle *refuse to
   start the updater* (source-verified, §Info.plist above) — the app would
   never exercise the menu item or the policy until the key is set, and a
   shipped release would carry a hard configuration error. The
   "matches nothing" semantics are kept; the placeholder is loudly flagged at
   boot, in CI (the appcast step warns), and in the docs.
6. **The `SPARKLE_ED_KEY` secret is the exported file's *content*** (a base64
   string) — `generate_keys -x` writes exactly what `--ed-key-file -` reads
   (source-verified in `common_cli/Secret.swift` + `sign_update/main.swift`).
   The workorder's "(base64)" is honored; the guide says explicitly *not* to
   base64 the file again, and the script refuses a double-encoded value with a
   message naming that mistake.
7. **`SURAMAK_SMOKE_SETTINGS`** (3 lines, smoke modes only, the M9c
   `SURAMAK_SMOKE_MODELS` precedent) opens the Settings route so the new
   section can be captured headlessly — the M9/M10B capture pattern. Inert in
   normal runs.
8. **ci.yml's macOS bundle now carries `updates`** (the workorder allowed "a
   bounded macOS `--features updates` compile step — only if the framework
   fetch is cheap and pinned"; it is: one sha256-verified 15 MB download).
   Taking it one step further, the existing bundle smoke test then launches a
   real bundle with Sparkle embedded — the only CI-side check of the
   embed+rpath+start contract. No new CI steps beyond fetch + the env.
9. **The delta fetch is gated** (`GITHUB_ACTIONS=true`, or
   `SURAMAK_APPCAST_HISTORY=1` locally) so a local run never reaches for the
   network, and it is best-effort (`gh` failures never fail the release). The
   first release has no previous archives → no deltas, as documented by
   Sparkle.
10. **The appcast's `--download-url-prefix`** is built from `GITHUB_REF_NAME`
    (the tag, e.g. `v0.2.1`) → `…/releases/download/v0.2.1/` — the assets are
    attached to that same release by the release job.
11. **Logging shape**: the event callback logs the stable `event.name()` plus
    the typed payload fields (version/choice/message) rather than the raw JSON
    payload — brief, main-thread-safe, and grep-able as `updates:` lines.

## Boundaries (honest)

- **The entire update cycle is owner-verify** (USER_SMOKE §32): check → prompt
  → download → in-place install → relaunch, plus the first-cycle behavior with
  a real key. Nothing in it can execute on Linux: `Sparkle.framework` and the
  tools are macOS binaries, and the crate requires a live AppKit loop.
- **What Linux verified** is everything above: the stub + settings round-trips
  + plist/pin/workflow/appcast-script contracts (real tests), the pinned
  download against the real archive, the real app booting with the module
  (smoke + headless Settings capture), and a `cargo check`/`clippy -D warnings`
  of the verbatim macOS module against the real crate **for the darwin
  target**. What remains: the framework **link** (linker-side), dyld
  resolution at launch, and every runtime behavior — those are the macOS
  CI/release builds' and the owner's Mac's to validate.
- **`scripts/make-app.sh` cannot run on Linux** (PlistBuddy/iconutil/codesign
  are macOS-only). Its idempotence is by construction (`rm -rf` the bundle,
  fresh copies, re-sign) and its real execution is the macOS CI/release runs;
  the *fetch* script's idempotence is verified for real here (7 ms quiet
  re-run).
- **Ad-hoc signing + Sparkle**: the framework is ad-hoc signed with the app
  (`--deep`), which is what the current release flow does for everything. The
  install cycle from an ad-hoc-signed app is part of the owner's first real
  cycle; §32 asks for the observed result. Developer ID + notarization stay
  their own decision (PLAN §8.6) — Sparkle's docs note Library Validation
  matters only once the hardened runtime is enabled, which this build does not.
- **No key material anywhere in the repo**: the private key exists only as the
  owner's `SPARKLE_ED_KEY` secret (and the local export file the guide says to
  delete); the public key is a placeholder until the owner's one-time setup.
- **Before the key setup** the shipped app finds the (missing or
  differently-signed) feed but can verify nothing — it logs the placeholder
  warning at every boot and the release pipeline warns; the updater stays
  effectively dormant. This is the documented pre-key state, not a failure.
- **`cargo check --target aarch64-apple-darwin` for the whole workspace still
  fails at `ring`'s C build** (the pre-existing M1.5 class, `cc: error:
  unrecognized command-line option '-arch'`) — the focused probe (§5) is the
  workaround, exactly as in M10B.
- **Deltas are best-effort by design**: they need previous releases' archives
  (CI fetches them); a missing/failed fetch only means a full download for the
  user, never a broken feed.

## Owner key setup (one-time, on the Mac)

```bash
# 0. Get the tools (pinned + sha256-verified; also done by any make-app run):
./scripts/fetch-sparkle.sh                 # → build/sparkle/2.9.6 (framework + bin/)

# 1. Generate the EdDSA keypair. It lands in your login keychain; the public
#    key is printed (copy it). One keypair serves all Suramak releases.
./build/sparkle/2.9.6/bin/generate_keys

# 2. Put the printed public key into packaging/Info.plist, replacing the
#    placeholder:
#      <key>SUPublicEDKey</key>
#      <string>THE_PRINTED_KEY</string>
#    (Also delete the "M12 PLACEHOLDER" comment above it, or leave it as
#    history — the value is what matters.) Commit that one-line change.

# 3. Export the private key and store it as the repo secret. The exported file
#    IS the base64 key string that --ed-key-file - expects — paste its content
#    as-is, do NOT base64 it again:
./build/sparkle/2.9.6/bin/generate_keys -x /tmp/sparkle_ed_key
pbcopy < /tmp/sparkle_ed_key
#    → GitHub → repo → Settings → Secrets and variables → Actions →
#      New repository secret → name: SPARKLE_ED_KEY → paste → Add.
rm -f /tmp/sparkle_ed_key                  # no key material left on disk

# 4. Re-cut the release (or push the next tag). Expected in the macOS job:
```
