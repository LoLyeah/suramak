### 1.4 whisper build flags — portable AVX2 baseline + the CRT match

whisper.cpp is built by `whisper-rs-sys`'s build script through the `cmake` crate. Its build script **forwards every environment variable starting with `WHISPER_`/`GGML_`/`CMAKE_` to CMake as a `-D` define** (`whisper-rs-sys-0.15.0/build.rs`, the `env::vars()` loop). That is the wiring point; the flags live in the `windows` job's `env` block (target-scoped by construction — no other job is affected):

| Variable | Purpose |
|---|---|
| `GGML_NATIVE=OFF` | no build-host tuning (`-march=native` class); with native off, ggml's own `INS_ENB` defaults enable the explicit SSE4.2/AVX/AVX2/BMI2 family — the AVX2 x86-64 baseline D4 asks for. Runtime dispatch for lower tiers is ggml's own. |
| `GGML_AVX2=ON` | the explicit feature level, stated rather than implied. (ggml's `GGML_AVX512*` options default OFF.) |
| `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded` | static CRT (`/MT`) for whisper.cpp/ggml. |
| `CMAKE_POLICY_DEFAULT_CMP0091=NEW` | whisper.cpp declares `cmake_minimum_required(VERSION 3.5)`, so CMP0091 (the policy that owns `CMAKE_MSVC_RUNTIME_LIBRARY`) is left **unset**; `CMAKE_POLICY_DEFAULT_CMP<NNNN>` is CMake's documented switch for exactly that case (verified against the local CMake 4.2 docs and `Modules/Platform/Windows-MSVC.cmake`). Without it the define is ignored and whisper would build `/MD` → `LNK2038`. |
| `CMAKE_TOOLCHAIN_FILE=scripts/windows/msvc-static-crt.cmake` | reaches the CMake deps that do **not** forward env vars — libopus (`opusic-sys`), whose CMakeLists overrides `CMAKE_MSVC_RUNTIME_LIBRARY` from its own `OPUS_STATIC_RUNTIME` option. cmake-rs reads `CMAKE_TOOLCHAIN_FILE` from the environment itself (`cmake-0.1.58/src/lib.rs:450`), and whisper-rs-sys forwards it too. |

`cc`-built C deps need nothing: cc-rs 1.8.0 reads `CARGO_CFG_TARGET_FEATURE` and passes `-MT` instead of `-MD` when `crt-static` is present (SQLite, ring). Note cc-rs never passes `-MTd`/`-MDd` — the release CRT variant is used in debug profiles too, so there is no debug/release `LNK2038` split between cc objects, CMake objects (Release) and rustc's debug builds.

`scripts/windows/msvc-static-crt.cmake` (new) does three things, all Windows-host-guarded (a strict no-op elsewhere — verified by running it through CMake on this Linux box, both as a toolchain file and in `cmake -P` script mode: no messages, configure unchanged):

1. `set(CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreaded" CACHE STRING "" FORCE)`.
2. `set(OPUS_STATIC_RUNTIME ON CACHE BOOL "" FORCE)` — the only way to reach libopus's own switch.
3. Ninja-only `cl.exe` discovery (PATH first, then a standard VS 2022 install glob): defining a toolchain file makes cmake-rs skip its own `-DCMAKE_C_COMPILER=<cl>` hint (`cmake-0.1.58/src/lib.rs:780`), and `opusic-sys` picks Ninja whenever `ninja` exists — as on the GitHub runners. The block only acts if `cl.exe` is actually found; otherwise CMake's own detection runs unchanged.

## 3. Deviations and notes (with whys)

1. **`cargo check --target x86_64-pc-windows-msvc -p suramak-core` does not succeed on this VPS** — the workorder's verification bullet names it, but the workorder's own environment-facts paragraph names `ring` as one of the C deps that *must* fail here, and `suramak-core` pulls `ring`, bundled SQLite and bundled libopus. The local Windows-target gate is therefore the C-free set (`suramak-taps`, `suramak-glass` — checked and clippy-checked on the Windows target, §2.2) plus the tree audits; the C-backed crates are proven by the runner, per the workorder's stated boundary. Exact error pasted in §2.2.
2. **No target-specific deps were needed** (the workorder's "where needed"): the Windows graph already resolves the right platform crates and excludes the macOS-only ones (§1.2). Nothing was added to any manifest — which is also why the dep trees are provably unchanged.
3. **No `cfg` changes were needed either** (§1.1) — M4/M9/M12/M13a had already fenced the four named seams, and the workspace-wide audit found no un-gated Unix-only code. This is stated as an *audit result with evidence*, not as a compile proof: the workspace has never been compiled for Windows, and the runner is the first place that happens.
4. **The Linux SIGILL hypothesis was not attempted.** D4 notes the linux runner's SIGILL "may stem from build-host-tuned code" and that M14a "checks whether the same flag fixes it, but does not block on it". Changing the `linux` job's whisper build flags would (a) contradict this workorder's "append; existing jobs untouched" and (b) modify a green job's C build in a slice whose proof lives elsewhere. Logged for the owner as its own small experiment (`GGML_NATIVE=OFF` in the linux job).
5. **`cargo test` on Windows writes one database under `%APPDATA%`**: the CLI polish test redirects the data dir via `XDG_DATA_HOME`, which `directories` ignores on Windows — the test is self-contained and still passes (it inserts and reads back through the same path), it just lands in the real app-data dir instead of a temp root. Harmless for CI; the M14b path work (`%LOCALAPPDATA%`) will revisit it.
6. **The first Windows clippy run is a first-ever lint of platform-only code** (`suramak-glass/src/windows.rs`, the `cfg(windows)` arm in `app/mod.rs`). A platform-specific lint would be a legitimate job failure; the fix would be a source tweak, not a config change.
7. **Local Windows builds need the same five env vars** — CI-only wiring would make a developer's plain `cargo build` fail with `LNK2038`. That is why the contract is documented in `.cargo/config.toml` and in §5 rather than hidden in the workflow.
