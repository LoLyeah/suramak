## 2. The version pair — the risk the workorder named

**`android-activity` 0.6.1 + `androidx.games:games-activity` 3.0.5.**

How that was established (not guessed). The crate vendors AGDK's GameActivity
C++ glue and registers its Java natives dynamically:

- `android-games-sdk/…/GameActivity.cpp` holds a 24-entry `JNINativeMethod`
  table (`g_methods`) and calls `RegisterNatives` from `GameActivity_register`.
  A single wrong descriptor there is **fatal at startup** (`LOG_FATAL
  "RegisterNatives failed … aborting"`), so the AAR's `GameActivity` class must
  declare exactly those 24 native methods.
- I extracted the table from the C++ (joining its multi-line string literals)
  and each candidate AAR's `com.google.androidgamesdk.GameActivity` from Google
  Maven (`javap -s -p`), then compared the `(name, descriptor)` sets:

| AAR | natives | vs. crate's 24 |
|---|---|---|
| 2.0.2 | 22 | **incompatible**: `onTouchEventNative` is `(JLandroid/view/MotionEvent;)Z` where the glue registers `(JLandroid/view/MotionEvent;IIIIIJJIIIIIIFF)Z`; `onSoftwareKeyboardVisibilityChangedNative` and `onEditorActionNative` do not exist |
| **3.0.5** | 24 | **exact match** (names and descriptors) |
| 4.4.2 | 24 | exact match as well |

Also checked, because the glue looks them up at registration time:
`finish()`, `setWindowFlags(II)`, `getWindowInsets(I)`,
`getWaterfallInsets()`, `setImeEditorInfoFields(III)` and
`androidx.core.graphics.Insets.{left,right,top,bottom}` — all present in 3.0.5.

**Why 3.0.5 and not 4.4.2:** both satisfy the JNI contract, but 3.0.5 is the
contract the vendored glue was imported against (the 24-method table with the
keyboard/editor-action callbacks is the 3.0-era AGDK surface). 4.4.2 adds
static-handle plumbing (`nativeHandle`/`nativeHandleOwner`) that nothing in this
stack exercises, so it buys risk without benefit. If M13c needs a newer AGDK,
4.4.2 is the first candidate — the table check above is how to confirm it again.

`games-activity` is pulled transitively with `androidx.appcompat`, because
`GameActivity extends AppCompatActivity` in every 2.x/3.x/4.x release; the
manifest theme therefore descends from `Theme.AppCompat.NoActionBar`
(`android/app/src/main/res/values/themes.xml`). Getting that wrong throws
" You need to use a Theme.AppCompat theme" before any of our code runs.

## 5. Finding: winit 0.30.13 drops Android IME text (and what the spike does about it)

This is the one finding that changes M13c's scope, so it is stated with its
evidence.

`android-activity` 0.6.1 exposes GameTextInput's editing state twice:

1. as `AndroidApp::take_text_input_state()` (polling), and
2. through `input_events_iter()`, where `InputIteratorInner::next()` calls
   `take_text_input_state()` and emits `InputEvent::TextEvent(state)`
   (`android-activity-0.6.1/src/game_activity/mod.rs`, the
   `ime_text_input_state_checked` block).

winit 0.30.13's Android backend handles exactly two input variants —
`InputEvent::MotionEvent` and `InputEvent::KeyEvent` — and sends everything else
to `_ => warn!("Unknown android_activity input event {event:?}")`
(`winit-0.30.13/src/platform_impl/android/mod.rs::handle_input_event`). Since
the iterator already consumed (and cleared) the text state, the text is gone:
winit's `ApplicationHandler` never sees an `Ime` event, so egui's `TextEdit`
receives nothing from the soft keyboard. `set_ime_allowed` *does* work (it maps
to `show_soft_input`), so the keyboard appears — it just cannot type.

The spike therefore carries a **spike-local IME bridge** so check 1 can still
judge egui's editing quality instead of failing on a plumbing gap:

```
GameActivity.stateChanged(State, boolean)        (Kotlin, MainActivity)
  → super.stateChanged(...)                      (keeps GameActivity's bookkeeping)
  → nativeImeText(text, selectionStart, selectionEnd)   (JNI, platform.rs)
  → SpikeState.text + egui caret moved to the IME selection
```

The Text tab exposes it as a checkbox (default **on**) and counts both paths:
`IME updates` (bridge) versus `winit key-text chars` (what winit delivers —
0 for soft keyboards). Unticking the box reproduces the gap on the device.

**What this means for M13:** egui text editing is *testable* (the gate can judge
it), but the production path in M13c must own this bridge properly — either
winit learns to forward `InputEvent::TextEvent` as `WindowEvent::Ime`
(upstream or fork patch), or `suramak-android` owns a documented
GameTextInput↔egui adapter. The spike's version is deliberately minimal:
it replaces the buffer wholesale, tracks the IME's selection, and does not push
local (hardware-key) edits back into GameTextInput.

## 6. What the app does

One `MainActivity : com.google.androidgamesdk.GameActivity`, no other Kotlin
class, no Compose. It loads `libsuramak_android_spike.so` in a static
initialiser (before `super.onCreate` calls `initializeNativeCode`), then:

- pushes window insets (`systemBars | displayCutout`, plus the IME inset) to
  Rust whenever `onApplyWindowInsets` fires and again on resume;
- installs an always-enabled `OnBackPressedCallback` that forwards to Rust and
  never finishes the Activity;
- overrides `stateChanged` for the IME bridge described above;
- exposes `postRecreate()` so Rust can call `Activity.recreate()` over JNI
  (posted to the UI thread through `View.post` — the request originates on the
  `android_main` thread).

On the Rust side the four tabs are:

1. **Text** — multiline `TextEdit`, characters-received / deletions counters,
   IME-update counter, bridge switch.
2. **Lifecycle** — probe `TextEdit`, resume count, surface-rebuild count, a
   "Recreate activity now" button.
3. **Motion** — a sine-driven bar, measured average fps and ms/frame over a
   120-frame window, frame count.
4. **Insets/back** — the five inset values in px and dp, inset-update count,
   intercepted-back count.

A verdict strip at the bottom shows `GO`/`WAIT` per check from that evidence,
and the header carries **M13B GO/NO-GO** plus a reset button.

State lives in a process-wide `OnceLock<Mutex<SpikeState>>`, not in the window
handler, because `android_main` runs again after an Activity recreation — that
is what makes the lifecycle check meaningful. The wgpu surface, adapter and
`egui_winit::State` are dropped on `suspended` and rebuilt on `resumed`; the
`Window` object is reused, since winit re-queries the current `ANativeWindow`
from `AndroidApp` on each handle request.

## 8. The honest boundary

**Built here, run only on the owner's device.** Nothing in this report says the
app launches: there is no phone, no emulator package and no system image on this
VPS, and the workorder scopes the emulator smoke to a later slice. What is
proven is that the APK exists, is correctly signed, carries the right manifest
and the right ABI library, exports the JNI surface both sides expect, and that
the Rust/Kotlin sources compile for `aarch64-linux-android`.

The risks that only the device can settle:

1. **wgpu on the device's Vulkan driver** — the desktop path uses lavapipe/
   llvmpipe; a phone driver may reject the surface config or the pipeline. The
   app logs the chosen adapter (`gpu: …` line in the verdict strip) and falls
   back to GLES if Vulkan yields no adapter.
2. **The IME bridge timing** — whether `stateChanged` fires early enough and how
   the caret behaves with autocorrect replacements and word-delete.
3. **Surface recreation** — whether drop-on-suspend/rebuild-on-resume is enough
   on the owner's OEM, or whether the `Window` also has to be replaced.
4. **`Activity.recreate()` from the shim** — the JNI call + `View.post` path is
   only exercised on hardware.
5. **Theme/insets cosmetics** — `Theme.AppCompat.NoActionBar` with transparent
   system bars; the inset numbers are what matter, not the look.

If check 1 fails with the bridge on, that is a genuine egui/IME quality No-Go
and triggers option C for text fields only. If it fails with the bridge off but
passes on, the finding is the winit gap (§5), not egui.

## 10. Handoff to M13c

1. **Own the IME bridge.** Decide between a winit patch (forward
   `InputEvent::TextEvent` → `WindowEvent::Ime::{Preedit,Commit}`) and a
   documented adapter in `suramak-android`. The spike's version is a probe, not
   a component: it replaces the whole buffer and never pushes local edits back.
2. **Make insets and back a typed contract** (`PlatformEvent` enum, per plan
   §M13c) instead of the four ad-hoc JNI functions used here.
3. **Keep the surface lifecycle rule** proven here: state outside the window,
   GPU objects dropped on suspend, rebuilt on resume.
4. **CI**: the `android-spike` job is compile/packaging proof only. When the
   emulator lane lands (plan §2.3), it should install this APK and assert the
   process reaches the first frame.
