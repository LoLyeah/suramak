# Comprehensive Code Audit Report: Suramak Rust Workspace

**Audit Target:** Suramak Workspace (`suramak-core`, `suramak-asr`, `suramak-cli`, `suramak-ui`, `suramak-playback`, `suramak-taps`, `suramak-glass`, `suramak-android`, `suramak-android-spike`)

**Toolchain:** `rustc 1.99.0`, `cargo 1.99.0` (Edition 2021, MSRV 1.85)  
**Date of Audit:** October 2026  
**Audit Scope:** Full static and architectural analysis of all crates in `./crates`, workspace root configuration, build scripts, packaging configurations, and platform integration seams.

---

## Executive Summary

Suramak is a native, local-first multi-platform audio transcription suite developed in Rust without webviews or external runtime dependencies like FFmpeg. It features on-device transcription via `whisper.cpp` (with Metal and Core ML acceleration on Apple Silicon), alternative transducer engines (`Parakeet` via `sherpa-onnx` and Apple `SpeechTranscriber`), multi-source recording, real-time provisional transcription, local SQLite storage, and optional audio-aware LLM transcript polishing.

This audit conducted a comprehensive analysis across security vulnerabilities, logic bugs, concurrency flaws/race conditions, and Rust best-practice violations. The codebase demonstrates high engineering discipline, clean separation of domain logic, comprehensive unit testing, and meticulous platform consideration. However, several critical and high-severity issues were identified—including a **deadlocking bug on transcription cancellation**, a **severe race condition and model corruption flaw during Core ML model hiding**, a **native memory leak in CoreAudio string management**, an **HTTP range resumption corruption bug in model downloads**, and **real-time safety violations within OS audio callbacks**.

### Critical Severity

#### SUR-CRIT-01: Thread Deadlock on Job Cancellation: `WorkerEvent::Cancelled` Not Recognized as Terminal in UI Bridge
- **Component:** `suramak-ui`
- **File & Lines:** [`crates/suramak-ui/src/runtime.rs#L1480-L1490`](file:///home/ubuntu/suramak/crates/suramak-ui/src/runtime.rs#L1480-L1490)
- **CWE:** CWE-833 (Deadlock)
- **Description:**
  In milestone M9e, cooperative job cancellation was introduced using `CancelToken`. When a cancellation signal is tripped during transcription, the worker thread cleanly aborts whisper inference and emits a terminal event `WorkerEvent::Cancelled { job_id }` across its channel before re-entering its main listening loop (`worker.recv()`).
  
  In the UI bridge thread (`run_bridge`), incoming worker events are consumed in an inner loop that determines when to finish processing the current job and return to listening for new jobs from `job_rx`:
  ```rust
  loop {
      match worker.recv() {
          Some(event) => {
              let terminal = matches!(
                  event,
                  WorkerEvent::Finished { .. } | WorkerEvent::Error { .. }
              );
              push(&queue, event);
              ctx.request_repaint();
              if terminal {
                  break;
              }
          }
          None => {
              push(&queue, worker_gone(job_id));
              ctx.request_repaint();
              break;
          }
      }
  }
  ```
  `WorkerEvent::Cancelled` was omitted from the `matches!` pattern for `terminal`. When a job is cancelled, `terminal` evaluates to `false`. The inner loop does not break; instead, it immediately calls `worker.recv()` again. However, the worker thread has already completed the job and is blocked in `while let Ok(job) = jobs.recv()` waiting for a subsequent job.
- **Impact:**
  The `suramak-ui-bridge` thread deadlocks permanently inside `worker.recv()`. Although `AppState` and `runtime.drain_worker()` register the cancellation and return to the Home view, any subsequent audio file or recording submitted for transcription will be sent to `job_tx`, which will remain unread in `job_rx` forever. The UI becomes stuck indefinitely on "Transcribing... 0%", requiring a full application restart to restore functionality.
- **Remediation:**
  Update the `terminal` condition in `run_bridge` to include `WorkerEvent::Cancelled`:
  ```rust
  let terminal = matches!(
      event,
      WorkerEvent::Finished { .. }
          | WorkerEvent::Error { .. }
          | WorkerEvent::Cancelled { .. }
  );
  ```

#### SUR-CRIT-02: File System Race Condition, Non-RAII Panic Leak, and Permanent Asset Corruption via Model Directory Renaming
- **Component:** `suramak-asr`, `suramak-ui`
- **File & Lines:** [`crates/suramak-asr/src/whisper.rs#L286-L320`](file:///home/ubuntu/suramak/crates/suramak-asr/src/whisper.rs#L286-L320), [`crates/suramak-asr/src/live.rs#L733-L750`](file:///home/ubuntu/suramak/crates/suramak-asr/src/live.rs#L733-L750), [`crates/suramak-ui/src/shutdown.rs#L73-L84`](file:///home/ubuntu/suramak/crates/suramak-ui/src/shutdown.rs#L73-L84)
- **CWE:** CWE-362 (Concurrent Execution using Shared Resource with Improper Synchronization / Race Condition), CWE-459 (Incomplete Cleanup)
- **Description:**
  `whisper.cpp` automatically loads Core ML encoder packages whenever a directory named `<model>-encoder.mlmodelc` exists alongside the GGML decoder binary. To force fallback to Metal or CPU, `suramak-asr` employs `with_encoder_hidden`:
  ```rust
  fn with_encoder_hidden<T>(model_path: &Path, f: impl FnOnce() -> T) -> T {
      let dir = models::encoder_dir_for(model_path);
      let hidden = hidden_encoder_path(&dir);
      let mut stashed = false;
      if dir.is_dir() {
          match std::fs::rename(&dir, &hidden) {
              Ok(()) => stashed = true,
              Err(err) => warn!(...),
          }
      }
      let out = f();
      if stashed {
          if let Err(err) = std::fs::rename(&hidden, &dir) {
              warn!(...);
          }
      }
      out
  }
  ```
  Where `hidden_encoder_path` computes:
  ```rust
  parent.join(format!(".{name}.hidden-{}", std::process::id()))
  ```
  This implementation suffers from three critical vulnerabilities:
  1. **Thread Race Condition:** `hidden_encoder_path` relies exclusively on `std::process::id()`. When live transcription is active, the `suramak-live-decode` thread repeatedly evaluates 4-second audio slices in the background. If the user simultaneously initiates a batch transcription on the worker thread, both threads share the identical hidden path. One thread renames the directory while the other fails or operates against a missing model.
  2. **Non-RAII Panic Unwinding:** `with_encoder_hidden` executes `let out = f();` without an RAII drop guard or `catch_unwind`. If `f()` panics (e.g. in underlying C++ inference initialization), the restoration rename is skipped entirely.
  3. **Hard-Exit Asset Abandonment:** When a live recording session is interrupted by application quit, `LiveDecoder` is given an uncancelled token (`CancelToken::new()`). If `with_encoder_hidden` is active when the 250ms quit grace period expires, `shutdown::hard_exit` invokes `libc::_exit(code)`. The process terminates instantly, stranding the Core ML model at `.<model>-encoder.mlmodelc.hidden-<pid>`.
- **Impact:**
  Permanent loss of Core ML hardware acceleration. After such an event, `dir.is_dir()` returns `false` on every subsequent launch, and Core ML is disabled permanently until the user navigates to the filesystem and manually repairs hidden directory names.
- **Remediation:**
  1. Implement an RAII scope guard (`struct StashedEncoderGuard<'a>`) whose `Drop` implementation ensures `std::fs::rename(&hidden, &dir)` runs even during panic unwinding.
  2. Include thread identifier or a cryptographic nonce (`nanoid` or UUID) in the temporary hidden directory path: `format!(".{name}.hidden-{}-{:?}", std::process::id(), std::thread::current().id())`.
  3. Introduce process-wide synchronization (`std::sync::Mutex` or `parking_lot::ReentrantMutex`) guarding filesystem model state transitions.
  4. Ensure `LiveDecoder` passes a cancellable token that is cancelled during quit teardown before `libc::_exit` is reached.

### High Severity

#### SUR-HIGH-01: CoreFoundation Memory Leak via Incorrect Retain Rule in CoreAudio String Property Extraction
- **Component:** `suramak-taps`
- **File & Lines:** [`crates/suramak-taps/src/macos.rs#L241-L274`](file:///home/ubuntu/suramak/crates/suramak-taps/src/macos.rs#L241-L274)
- **CWE:** CWE-401 (Missing Release of Memory after Effective Lifetime / Memory Leak)
- **Description:**
  In `suramak-taps/src/macos.rs`, `string_property` queries properties from CoreAudio objects using `AudioObjectGetPropertyData`:
  ```rust
  fn string_property(object: AudioObjectId, selector: u32) -> Result<String, TapError> {
      ...
      let status = unsafe {
          AudioObjectGetPropertyData(
              object,
              &address,
              0,
              ptr::null(),
              &mut size,
              &mut value as *mut CFStringRef as *mut c_void,
          )
      };
      ...
      // SAFETY: non-null CFStringRef owned by CoreAudio; `wrap_under_get_rule` retains.
      Ok(unsafe { CFString::wrap_under_get_rule(value) }.to_string())
  }
  ```
  In Apple's CoreAudio HAL specifications, string properties fetched via `AudioObjectGetPropertyData` follow the **Create Rule** (`CF_RETURNS_RETAINED`): the HAL returns a `CFStringRef` with a retain count already incremented (+1), placing responsibility on the caller to release it.
  
  By wrapping `value` using `CFString::wrap_under_get_rule(value)`, the wrapper calls `CFRetain(value)` (incrementing retain count to +2). When the Rust `CFString` wrapper goes out of scope, it calls `CFRelease` once (leaving the count at +1). The reference returned by CoreAudio is never released.
  
  Notably, in the sibling function `optional_string_property` ([`crates/suramak-taps/src/macos.rs#L279-L308`](file:///home/ubuntu/suramak/crates/suramak-taps/src/macos.rs#L279-L308)), the author documented this exact requirement:
  > *"Uses the create rule: CoreAudio property reads hand the caller a +1 CFStringRef ..., so `wrap_under_create_rule` takes that reference instead of leaking it."*
  However, `string_property` was never updated to match.
- **Impact:**
  Every call to `string_property` (invoked repeatedly when enumerating audio processes, checking device UIDs, and configuring taps) permanently leaks a CoreFoundation string object in memory. Over prolonged recording sessions or frequent process polling, this causes progressive memory bloat.
- **Remediation:**
  Change line 273 to use `wrap_under_create_rule`:
  ```rust
  Ok(unsafe { CFString::wrap_under_create_rule(value) }.to_string())
  ```

#### SUR-HIGH-02: HTTP Range Resumption Body Corruption & Permanent Download Lockout on Partial Failure
- **Component:** `suramak-core`
- **File & Lines:** [`crates/suramak-core/src/download.rs#L47-L86`](file:///home/ubuntu/suramak/crates/suramak-core/src/download.rs#L47-L86)
- **CWE:** CWE-436 (Interpretation Conflict), CWE-20 (Improper Input Validation)
- **Description:**
  The `download_with_progress` function implements HTTP Range resumption when a partial file (`dest.part`) exists:
  ```rust
  if existing_bytes > 0 {
      debug!("resuming from byte {existing_bytes}");
      req = req.header("Range", format!("bytes={existing_bytes}-"));
  }

  let mut resp = req.send()?;
  if !resp.status().is_success() && resp.status().as_u16() != 206 {
      return Err(SuramakError::Http(resp.error_for_status().unwrap_err()));
  }

  let mut file = std::fs::OpenOptions::new()
      .create(true)
      .append(true)
      .open(&part_path)?;
  ```
  Two critical failure modes exist in this flow:
  1. **Server Ignores Range (Returns 200 OK):** Many CDNs, proxies, or origin endpoints ignore byte-range headers or reply with `200 OK` sending the complete payload from byte 0. Because `resp.status().is_success()` evaluates to `true` for 200, the response is accepted, and the entire download is appended to `existing_bytes` via `.append(true)`. The resulting `.part` file contains duplicated headers/data, failing SHA-256 verification and consuming double disk space.
  2. **Uncleaned Partial Files on Failure (HTTP 416 Lockout):** If a download fails checksum verification at line 81 or is interrupted after reaching the expected file size, `part_path` is left on disk. On the next invocation, `existing_bytes` equals or exceeds the total file length. The request sends `Range: bytes=<len>-`, causing the server to respond with `HTTP 416 Range Not Satisfiable`. Line 54 rejects 416, returning an error without deleting `.part`. All future download attempts fail immediately with HTTP 416 until manual terminal intervention clears the `.part` file.
- **Impact:**
  Silent corruption of downloaded model binaries, wasted network bandwidth, and permanent user lockout from model downloads after network interruptions.
- **Remediation:**
  1. Verify response status when `existing_bytes > 0`: If `resp.status() == StatusCode::OK` (200), truncate the file and start from byte 0 instead of appending.
  2. If the server returns HTTP 416, or if SHA-256 validation fails, automatically remove `part_path` before returning the error.

#### SUR-HIGH-03: Audio Thread Priority Inversion and Dynamic Memory Allocation in Real-Time Input Stream Callback
- **Component:** `suramak-asr`
- **File & Lines:** [`crates/suramak-asr/src/capture.rs#L823-L841`](file:///home/ubuntu/suramak/crates/suramak-asr/src/capture.rs#L823-L841)
- **CWE:** CWE-667 (Improper Locking), CWE-400 (Uncontrolled Resource Consumption)
- **Description:**
  In `suramak-asr/src/capture.rs`, the CPAL input stream callback processes incoming audio blocks via `accumulate`:
  ```rust
  fn accumulate(
      samples: &Mutex<Vec<f32>>,
      rms_bits: &AtomicU32,
      rolling: &mut RollingRms,
      data: &[f32],
      channels: usize,
  ) {
      if data.is_empty() {
          return;
      }
      let mut buffer = samples
          .lock()
          .unwrap_or_else(|poisoned| poisoned.into_inner());
      for mono in mono_mixdown(data, channels) {
          buffer.push(mono);
          rolling.push(mono);
      }
      rms_bits.store(rolling.value().to_bits(), Ordering::Relaxed);
  }
  ```
  In modern audio subsystems (CoreAudio on macOS, ALSA/JACK/PulseAudio on Linux, WASAPI on Windows), the audio device input callback is invoked from an OS real-time scheduled thread. The audio processing callback violates essential real-time programming rules:
  1. **Locking Standard Mutexes:** `samples.lock()` acquires an OS-level mutex (`std::sync::Mutex`). The UI thread and runtime also lock `samples` (e.g. during `take_live_chunk()` or when finalizing the session at stop). If the main thread holds the mutex while rendering or doing layout, the real-time audio thread blocks, causing severe priority inversion.
  2. **Heap Allocation on the Audio Thread:** `mono_mixdown` creates a new heap-allocated `Vec<f32>` on every single buffer delivery. Furthermore, `buffer.push(mono)` triggers heap allocations and memory reallocations inside the callback. Heap allocators take global locks and may trigger system calls, page faults, or memory compaction.
- **Impact:**
  Buffer underruns (xruns), audible dropouts, stuttering, and missed audio frames during mic or system audio recording.
- **Remediation:**
  Use a lock-free, allocation-free Single-Producer Single-Consumer (SPSC) ring buffer (e.g. using the `rtrb` or `ringbuf` crates). The audio callback writes raw samples into the ring buffer lock-free without allocating. A background thread drains the ring buffer, resamples, and updates the shared storage vector.

#### SUR-HIGH-04: Non-Atomic Segment Upsert & Stale Segment Retention in SQLite Transcript Storage
- **Component:** `suramak-core`
- **File & Lines:** [`crates/suramak-core/src/store.rs#L66-L107`](file:///home/ubuntu/suramak/crates/suramak-core/src/store.rs#L66-L107)
- **CWE:** CWE-404 (Improper Resource Shutdown or Release), CWE-460 (Improper Cleanup on Additional Resource Initialization)
- **Description:**
  1. **Missing Transaction Wrapper:** `Store::insert_transcript` executes `INSERT INTO transcripts` followed by `upsert_segments`, which iterates over every segment executing independent `INSERT INTO segments ... ON CONFLICT DO UPDATE` statements. SQLite runs each statement in autocommit mode unless wrapped in `conn.transaction()`. If the process is killed or encounters an error mid-iteration, a partial transcript header with incomplete segments remains committed in the database.
  2. **Stale Segment Accumulation:** `upsert_segments` updates segments matching `(transcript_id, idx)`. If a transcript originally has 20 segments (indices 0..19) and is subsequently re-transcribed or polished into 12 segments (indices 0..11), `upsert_segments` updates indices 0..11, leaving stale indices 12..19 intact. When `get_transcript` is called:
     ```sql
     SELECT idx, start_ms, end_ms, text FROM segments WHERE transcript_id = ?1 ORDER BY idx
     ```
     It reads all 20 segments, concatenating the 12 new segments with 8 outdated segments.
  3. **Unenforced Foreign Keys:** `Store::init()` defines `REFERENCES transcripts(id) ON DELETE CASCADE`, but does not execute `PRAGMA foreign_keys = ON;`. In SQLite, foreign keys are disabled by default on every new database connection unless explicitly enabled via PRAGMA. If the database is ever opened with standard SQLite tooling or different compile flags, cascades will not fire.
- **Impact:**
  Silent data corruption in transcript history, orphaned transcript segments, database inconsistencies, and degraded insert performance.
- **Remediation:**
  1. Wrap batch operations in explicit transactions: `let tx = self.conn.transaction()?; ... tx.commit()?;`.
  2. In `upsert_segments`, delete excess segments: `DELETE FROM segments WHERE transcript_id = ?1 AND idx >= ?2`.
  3. Execute `PRAGMA foreign_keys = ON;` in `Store::init()`.

#### SUR-MED-01: Unbounded Zip Decompression (Zip Bomb) and Multi-Thread PID Collision in `extract_zip`
- **Component:** `suramak-core`
- **File & Lines:** [`crates/suramak-core/src/download.rs#L245-L357`](file:///home/ubuntu/suramak/crates/suramak-core/src/download.rs#L245-L357)
- **CWE:** CWE-409 (Improper Handling of Highly Compressed Data / Zip Bomb), CWE-362 (Race Condition)
- **Description:**
  In `extract_entries`:
  ```rust
  let mut sink = std::fs::File::create(&out)?;
  std::io::copy(&mut entry, &mut sink)?;
  ```
  `std::io::copy` decompresses the zip stream until EOF with no limitation on total uncompressed byte size or per-file size. An archive containing a malicious recursive compression payload (zip bomb) will decompress until disk space is exhausted.
  
  Additionally, temporary extraction directories are generated by:
  ```rust
  fn temp_sibling(dest_dir: &Path) -> PathBuf {
      ...
      parent.join(format!("{name}.{}.tmp", std::process::id()))
  }
  ```
  If two threads in the same process initiate extraction on the same destination directory simultaneously, both threads construct identical sibling directories, causing file collisions, premature `remove_dir_all` deletions, and extraction failures.
  
  Finally, `prefix` is identified using:
  ```rust
  let prefix = archive.file_names().next().map(|n| n.split('/').next().unwrap_or("").to_string()).unwrap_or_default();
  ```
  Zip file specifications do not mandate deterministic entry ordering. If the first entry is a metadata file (e.g. `__MACOSX/` or `PaxHeaders`), `prefix` is miscalculated, causing valid model files to be skipped and triggering an error: `archive contains no files under '<prefix>/'`.
- **Impact:**
  Denial of service via disk exhaustion, and intermittent extraction failures on multi-threaded downloads or archives with non-standard entry ordering.
- **Remediation:**
  1. Wrap `entry` with `std::io::Read::take` enforcing a reasonable upper boundary (e.g. 5 GB max uncompressed size).

#### SUR-MED-02: Abrupt Process Termination via `libc::_exit` Bypassing Destructors and SQLite WAL Checkpoint
- **Component:** `suramak-ui`
- **File & Lines:** [`crates/suramak-ui/src/shutdown.rs#L73-L90`](file:///home/ubuntu/suramak/crates/suramak-ui/src/shutdown.rs#L73-L90)
- **CWE:** CWE-404 (Improper Resource Shutdown or Release)
- **Description:**
  In `crates/suramak-ui/src/shutdown.rs`, `hard_exit` is called on process quit:
  ```rust
  pub fn hard_exit(code: i32) -> ! {
      use std::io::Write as _;
      let _ = std::io::stdout().flush();
      let _ = std::io::stderr().flush();
      #[cfg(unix)]
      unsafe { libc::_exit(code) }
      #[cfg(not(unix))]
      std::process::exit(code)
  }
  ```
  This was introduced to work around a crash in GGML's static C++ destructor on macOS (`GGML_ASSERT([rsets->data count] == 0)`). However, terminating the process via `libc::_exit`:
  - Completely bypasses Rust stack unwinding and skips all `Drop` implementations.
  - Skips SQLite WAL (Write-Ahead Logging) checkpointing and flushing. Any in-memory SQLite pages or WAL indexes that have not synced to disk remain uncommitted, leaving `-wal` and `-shm` files on disk requiring recovery on next boot.
  - Abruptly severs active threads without giving them opportunity to finalize file writes.
- **Impact:**
  Increased risk of database inconsistency, orphaned lock files, and potential corruption of files being written at the moment of quit.
- **Remediation:**
  Properly track and drop active `WhisperContext` and `WhisperState` handles before invoking exit routines, allowing orderly shutdown of runtime threads and graceful closure of SQLite connections via standard `Drop`.

#### SUR-MED-03: Signed Integer Overflow on Long Audio Buffers in Parakeet Transducer FFI Call

- **File & Lines:** [`crates/suramak-asr/src/parakeet.rs#L435-L440`](file:///home/ubuntu/suramak/crates/suramak-asr/src/parakeet.rs#L435-L440)

#### SUR-MED-04: Potential Division by Zero and Integer Multiplication Overflow in Playback Resampler
- **Component:** `suramak-playback`
- **File & Lines:** [`crates/suramak-playback/src/engine.rs#L500-L504`](file:///home/ubuntu/suramak/crates/suramak-playback/src/engine.rs#L500-L504)
- **CWE:** CWE-369 (Divide by Zero), CWE-190 (Integer Overflow)
- **Description:**
  In `resample_mono`:
  ```rust
  let mut output = Vec::with_capacity(samples.len() * to as usize / from as usize + chunk);
  ```
  1. **Division by Zero:** If `from` is 0 (which can occur if an audio file reports an invalid sample rate of 0), `from as usize` causes a division by zero panic in both debug and release builds.
  2. **Multiplication Overflow:** On 32-bit architectures (e.g. 32-bit Android or x86 targets), `samples.len() * to as usize` can overflow 32-bit `usize` for audio longer than ~15 minutes at 48kHz, causing an integer overflow panic in debug mode and buffer under-allocation in release mode.
- **Impact:**
  Application crash or memory allocation failure when opening malformed or long audio files in playback mode.
- **Remediation:**
  Guard against `from == 0` and use checked or 64-bit arithmetic:
  ```rust
  if from == 0 || to == 0 {
      return Err(EngineError::new("invalid sample rate", false));
  }
  let capacity = (samples.len() as u64)
      .checked_mul(to as u64)
      .map(|v| (v / from as u64) as usize + chunk)
      .unwrap_or(samples.len());
  let mut output = Vec::with_capacity(capacity);
  ```

#### SUR-LOW-05: Asymmetric Full-Scale Integer Quantization Range Exceeding `[-1.0, 1.0]` Boundary

## Workspace & Dependency Security Audit

### 1. Unsafe Code Inventory

The workspace contains approximately 40 `unsafe` blocks, concentrated across:
1. `suramak-asr/src/whisper.rs`: C-FFI callbacks for whisper progress trampolines, abort hooks, and system info retrieval.
2. `suramak-asr/src/parakeet.rs`: Sherpa-ONNX C API calls for offline recognizers, stream results, and token arrays.
3. `suramak-taps/src/macos.rs`: CoreAudio HAL FFI calls and Objective-C runtime messaging.
4. `suramak-glass/src/macos.rs` & `windows.rs`: AppKit NSView swizzling and Windows DWM backdrop configuration.
5. `suramak-ui/src/instance_windows.rs`: Win32 Token, Event, and Mutex API interactions.
6. `suramak-ui/src/shutdown.rs`: Direct syscall invocation of `libc::_exit`.

*Assessment:* The unsafe blocks interacting with C libraries generally uphold sound pointer lifetime invariants, but the FFI integer cast in `parakeet.rs` (SUR-MED-03) and the CoreAudio retain rule in `suramak-taps` (SUR-HIGH-01) represent real bugs in unsafe code boundaries.

### 2. Dependency Graph & Features Review
- **TLS Backend:** The workspace consistently pins `reqwest` with `default-features = false` and `rustls-tls`, avoiding OpenSSL C-binding vulnerabilities and dynamically linked OpenSSL dependencies.
- **Audio Decoding:** `symphonia` and `symphonia-adapter-libopus` compile pure-Rust and bundled C decoders, completely eliminating FFmpeg runtime command injection and dynamic linking liabilities.
- **SQLite Engine:** `rusqlite` is configured with `features = ["bundled"]`, ensuring a known, pinned SQLite version is statically compiled into the binary.
