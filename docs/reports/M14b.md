**Why the version is a checked literal, not a generated macro.** RC's preprocessor cannot read `CARGO_PKG_VERSION`, and passing it as `/D VER="0.3.0"` puts nested quoting into the resource-compiler command line — the one part of this slice that cannot be tested on this VPS (no `rc.exe`, no `llvm-rc`, no `windres`; §2.2). Instead the `.rc` carries the literals and `build.rs` **fails the build** if they disagree with Cargo:

```text
$ sed -i 's/FILEVERSION 0,3,0,0/FILEVERSION 0,2,9,0/' packaging/windows/suramak.rc && cargo build -p suramak-ui
error: failed to run custom build command for `suramak-ui v0.3.0`
  M14b: packaging/windows/suramak.rc is out of date — expected "FILEVERSION 0,3,0,0"
  (CARGO_PKG_VERSION = 0.3.0). Update the VERSIONINFO block.
exit 101        # restored afterwards; the restored tree builds (exit 0)
```

The check runs on **every** target, so a version bump that forgets the resource file fails the Linux and macOS jobs too — not only the Windows one.

### 1.2 Single-instance guard (D2)

Split in two, so the rules are host-testable and the Win32 half is small:

| Part | File | Contents |
|---|---|---|
| Pure protocol | `instance.rs` — `pub(crate) mod protocol` (`cfg(any(windows, test))`) | `mutex_name(sid)` → `Local\Suramak-SingleInstance-<SID>`, `event_name(sid)` → `Local\Suramak-Activate-<SID>`, `format_sid(revision, authority, &subs)` → `S-1-5-21-…`, `Claim {Primary, Secondary}`, `claim_from(already_exists)`, `SecondaryPlan {event_name, allow_foreground: true, exit_code: 0}`, `secondary_plan(sid)`. |
| Win32 | new `instance_windows.rs` (`cfg(windows)`, `main.rs:51`) | `user_sid()` (`OpenProcessToken` + `GetTokenInformation(TokenUser)`; the SID bytes are formatted by the pure `format_sid`, so no `ConvertSidToStringSidW`/`LocalFree`), `claim()` (`CreateMutexW` + `GetLastError() == ERROR_ALREADY_EXISTS`, handle leaked for the process lifetime), `watch_activation(cb)` (`CreateEventW(auto-reset)` + a `WaitForSingleObject` thread), `activate_running_instance()` (`AllowSetForegroundWindow(ASFW_ANY)` → `OpenEventW(EVENT_MODIFY_STATE)` → `SetEvent` → `CloseHandle`, returns `ActivationReport {signalled, foreground_granted, exit_code}`). |

The wiring, end to end:

* `main()` → `acquire_instance_lock(smoke.is_none())` (unchanged call site). Windows: `claim()` → `Primary` continues; `Secondary` → `activate_running_instance()`, **exits with the plan's code (0)** — logged (`signalled`, `foreground_granted`) when tracing is up, printed when not. A guard that cannot be created only warns and continues, exactly like the unix path.
* `main()` → after the loop exists and only when the guard ran, `watch_for_activation(&event_loop)` starts the watcher; each signal does `proxy.send_event(UserEvent::Activate)`.
* `App::user_event` → `UserEvent::Activate` → `Shell::activate_window()` (new, `shell.rs`): `set_minimized(false)`, `focus_window()`, `request_redraw()` — on the main thread, which is the only place winit allows window calls.

Choice notes, all deliberate:
- `Local\` namespace, per logon session, no privileges, fast user switching gets its own instance; the SID keeps RDP/other users apart (PLAN D2).
- The exiting process grants `AllowSetForegroundWindow(ASFW_ANY)` **before** signalling, per D2; a refused grant is not fatal (the signal still lands) and is reported in `ActivationReport.foreground_granted` so the caller logs it.
- Bounded race: a launch arriving between the first instance's `CreateMutexW` and its `CreateEventW` finds no event. The secondary side retries 40 × 25 ms (1 s) and then exits 0 anyway — the single-instance guarantee is the mutex; only the raise is lost, and it is logged.
- `UserEvent::Activate` is `#[cfg(windows)]`: nothing else constructs it, and an unconstructed variant is a `dead_code` error under `-D warnings` (the `GuardError` precedent, which that file's own comment documents).
- Smoke modes skip the guard (as on unix) and therefore skip the watcher — a transient smoke run can never swallow a real launch's activation.

### 1.3 Data paths

`crates/suramak-core/src/paths.rs`:

```rust
    platform_data_dir()                     // new, per-target

    if let Some(dir) = windows_data_dir(std::env::var_os("LOCALAPPDATA").as_deref()) {

    Ok(project_dirs()?.data_dir().to_path_buf())         // byte-for-byte the old body

```

### 1.4 Shell behaviour

**Ctrl-key audit — result: no binding change needed.** Every shortcut is `egui::Modifiers::COMMAND` (`keymap.rs` `BINDINGS`: R, E, Backspace) or `NONE` (Space, Esc, ↑, ↓); there is no `Modifiers::CTRL` and no `Modifiers::MAC_CMD` anywhere in the workspace (`grep -rn "MAC_CMD\|Modifiers::CTRL" crates/` → no hits outside the new test). `COMMAND` is resolved by egui-winit at the event source: `egui-winit-0.33.3/src/lib.rs`, the `ModifiersChanged` arm sets `modifiers.command = ctrl` off macOS and `= super` on macOS, and `Modifiers::cmd_ctrl_matches` requires `command` for a `COMMAND` pattern. So ⌘R/⌘E/⌘⌫ are Ctrl+R/Ctrl+E/Ctrl+Backspace on Windows with zero code change. Pinned by two new host-run tests (`the_command_bindings_are_ctrl_off_macos`, `ctrl_r_toggles_recording_like_command_r`) that assert the exact pressed-modifier sets each platform produces and drive a Ctrl+R through the real `dispatch` seam. No user-visible `⌘` string exists in the UI (the glyphs are in comments only), so there was nothing to re-label.

**Reveal in folder.** The app had **no** reveal action on any platform (`grep -rni "reveal\|showItemInFolder\|xdg-open"` → nothing), so per the workorder this is the helper plus one Windows-only entry:

* `reveal.rs`: `explorer_args(path)` (pure: exactly one argument, `"/select,<path>"` — `explorer`'s own syntax, so a spaced path stays one token) and `reveal_in_folder(path)` — `#[cfg(windows)]` spawns `explorer.exe` with that argument (no wait); the non-Windows stub returns `Unsupported` naming the command it would run. The module is compiled on every target and the caller is `cfg!(windows)`-gated (the `SYSTEM_AUDIO_OFFERED` pattern already in that file), so the host build type-checks the whole path instead of hiding it behind `#[cfg]`.
* Entry point: a tertiary "Show in Explorer" button in the existing Settings → **Recordings folder** row (`app/settings.rs`, `REVEAL_IN_FOLDER && form.keep_audio`), which creates the folder and then reveals it (`explorer` silently opens Documents for a missing path). There is no menu bar on any platform to hang a "menu entry" on — see §3.3.

## 3. Deviations and notes (with whys)

1. **The CI `tests` step does not run the new `suramak-ui` tests.** `ci.yml`'s `windows` job tests `-p suramak-core -p suramak-asr -p suramak-cli -p suramak-playback`; the guard's tests live in `suramak-ui`, so they compile (clippy `--all-targets`) but do not execute on the runner. The workorder assumed otherwise; the one-word fix (`-p suramak-ui`) is a `ci.yml` edit this workorder forbids. **Action for the orchestrator**: add `-p suramak-ui` to that step (it also brings the 200+ existing UI tests to Windows, which is a real, separate win). Until then, the Windows-only tests are compile-verified only.
2. **The CI model-cache path is now stale.** `ci.yml` caches/restores `~\AppData\Roaming\suramak\Suramak\data\models`; after §1.3 models live in `%LOCALAPPDATA%\Suramak\models`. The job still passes (the download step re-fetches; `actions/cache` only warns on a missing path), but the cache misses every run. Fix when `ci.yml` is next touched: path `~\AppData\Local\Suramak\models`, key unchanged. Not a correctness issue, not touched here.
3. **"Menu entry" became a Settings button.** The app has no menu bar on any platform (no in-app menu exists; macOS uses the AppKit menu only for Quit/Check for Updates). Inventing a menu for one Windows item would be more chrome than the action is worth, so the entry is a tertiary "Show in Explorer" button in the existing Settings → Recordings folder row. It reveals the **recordings folder** (not a file), because that is the folder the row already shows; the helper itself takes any path, so a future per-transcript "reveal the audio" entry needs no new plumbing.
4. **No console on Windows.** `windows_subsystem = "windows"` means the process has no console: every existing `eprintln!`/`println!` and the default `tracing_subscriber::fmt` stdout sink are invisible in a GUI launch (smoke modes still write their `build/*.txt` files, which is what the harness asserts). This is inherent to the attribute, not a defect, but it means the Windows app currently has **no visible log** — a file sink belongs to M14f (notifications) or M14h (docs), where "a failure is never silent in logs" is a stated requirement.
5. **`ActivationReport` carries the exit code**, and `main` exits with `report.exit_code` — so the value the test pins (`secondary_plan().exit_code == 0`) is the value actually executed, not a decorative constant.
6. **One activation edge is dropped, bounded**: a second launch that arrives while the first instance is still starting (before `App::shell` exists) posts `UserEvent::Activate`, which `user_event` discards when `shell` is `None`. The mutex guarantee is unaffected; only that one raise is lost (sub-second window, logged as `signalled: true`).
7. **The probe crate is not committed** (it lives under gitignored `build/`). The recipe is in §2.2 — recreate it to type-check Windows-only `suramak-ui` files from Linux. If M14c/M14d want it permanently, it belongs under `scripts/windows/` with its own `[workspace]`; that is a scope decision, not this workorder's.
8. **A Windows cross-check of `suramak-ui` from Linux now fails earlier**, in this crate's `build.rs` (`embed-resource` finds no `llvm-rc`), if the dependency graph ever gets past `ring`. Intentional: the manifest is `manifest_required()` — silently shipping an exe without DPI awareness/UTF-8/long paths would defeat the slice. The runner has `rc.exe`.
