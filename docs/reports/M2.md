## What was implemented

The app is now functional end-to-end: **drop a file (or pick one) → transcribe in-app with live progress → edit the transcript (autosaved) → it lives in the sqlite library → export to md/txt/json/srt/vtt** — inside the M1 Liquid-Glass shell (chrome strip / sidebar / main-pane composition unchanged; the static placeholder content is replaced by real views).

### `crates/suramak-ui/src/runtime.rs` — effects executor + worker bridge

- Owns the `Store` (opened from `paths::db_path()`), the settings snapshot (`Settings::load`) and the model resolution.
- Executes `Effect`s in order (worker submit, library insert, segment updates, transcript load, library refresh, export write) and feeds results back into `AppState` (effects produced by those results are queued, e.g. `SaveTranscript` → `RefreshLibrary`).
- **Worker wiring**: `suramak-asr`'s `Worker` (one background transcription thread, std mpsc) is owned by a thin **bridge thread** (`suramak-ui-bridge`) — the `Worker` handle is not shareable, and the UI must never block. The bridge forwards events into a mutex queue and calls `egui::Context::request_repaint()` on every event (Context is Send+Sync); the UI thread drains the queue in `about_to_wait`.
- In-app jobs **always save to the library DB** (unlike the CLI's opt-in `--db`) — that is the product behavior.

### `main.rs` / `shell.rs` — smoke modes and shell glue

- `shell.rs` now draws `AppState` via `app::views::draw` and returns the frame's `Effect`s; it installs `Context::set_request_repaint_callback` → `window.request_redraw()` so egui-side repaint requests (and the bridge thread's) wake the winit loop. M1 window/wgpu/glass code is unchanged.
- `main.rs` keeps the M1 plain smoke **exactly** (`SURAMAK_SMOKE_SECS=N` → N s of live app → `build/smoke_ok.txt` only when ≥1 frame presented → exit 0) and adds the scripted job mode:
  - `SURAMAK_SMOKE_JOB=<audio>` → on startup the app runs the **full in-app pipeline** (import → transcribe with the resolved default model → save to the library DB), then asserts the DB row through a **fresh `Store::open` connection** (row exists, ≥1 segment), prints `SMOKE-JOB-OK`, writes `build/smoke_job_ok.txt`, exits 0.
  - `SURAMAK_SMOKE_SECS` is the **watchdog**: not completed by then → exit 1, **no file** written (same "never a fake file" rule as M1). A missing input file fails fast (exit 1) instead of idling to the watchdog.
- Import paths: winit `WindowEvent::DroppedFile` (all platforms) + the home affordance; `HoveredFile`/`HoveredFileCancelled` drive the drop-zone highlight.

### Dependencies / CI

- `crates/suramak-ui/Cargo.toml`: `suramak-core`/`suramak-asr` path deps with **default features (`capture` OFF — the M1 target-gated `capture` feature was removed per M2 §3)**; new target-gated dep `rfd = "0.15"` under `[target.'cfg(any(target_os = "macos", target_os = "windows"))'.dependencies]` only.

## Deviations from the WORKORDER (with reasons)

1. **`capture` feature removed from `suramak-ui`'s macOS/Windows target dep.** M2 §3 says "default features; `capture` OFF", so the M1 target-gated `suramak-asr { features = ["capture"] }` line was dropped. Verified: `cargo tree -p suramak-ui --target aarch64-apple-darwin` no longer contains `cpal`. M3 re-enables it for recording.
2. **A bridge thread forwards worker events.** `suramak-asr::worker::Worker` owns a `Receiver` (not `Sync`) and `recv()` blocks, so it cannot be shared with, or polled from, the UI thread without blocking or busy-waiting. The bridge thread owns the single transcription worker and is the place the workorder's "call `egui::Context::request_repaint()` from the UI side when events arrive" happens. Still exactly one *transcription* worker thread; the bridge is a thin, job-serialized forwarder.
3. **`app/views.rs` added** for the frame dispatcher + M1 chrome strip. `app/mod.rs` is kept strictly egui-free (the workorder's "pure modules with no egui types" requirement), so the one egui entry point lives beside the area views; this is the split of the deleted `view.rs`.
4. **Playback is skipped** (workorder allows it: "selection follows playback position if trivial to do (else skip playback)") — the app has no audio playback engine yet (M3+), so there is nothing to follow. The M1 timeline strip is retained as a static element in the editor (ticks from the real transcript duration, playhead parked at the start) to keep the approved composition; it is decorative until playback lands.
5. **Model resolution ("auto") is an explicit, documented rule**: settings `model_id` (or a path) when installed → else the first installed model in `AUTO_MODEL_PREFERENCE` = `turbo-q5-0, small, base, tiny, turbo-q8-0, turbo` (shipped default first, then smaller/faster tiers). On this box only `tiny` is installed → the smoke job picks `tiny`, as the workorder states. Unit-tested against temp model dirs.
6. **Home import affordance on Linux**: the path field + Enter is present on **all** platforms (harmless on macOS/Windows, and needed there when the user prefers typing); the rfd `Choose file…` button is cfg-gated to macOS/Windows. The Linux build has no rfd code at all.
7. **Smoke job without `SURAMAK_SMOKE_SECS`** uses a 600 s default watchdog (with a printed notice) instead of hanging forever; CI and the acceptance always set both variables. Job mode also requires ≥1 presented frame before success (same rule as M1's plain smoke).
8. **`Cargo.lock` grew by ~537 lines** (rfd 0.15.4 + its *target-gated* tree: zbus/ashpd/xdg-portal for Linux, windows-sys for Windows). Cargo's lockfile is target-independent, so these appear in the lock but are **never built** on Linux (verified: `cargo tree -p suramak-ui --target x86_64-unknown-linux-gnu | grep -cE "rfd|zbus|ashpd|cpal"` → `0`). No new C dependency on any target we build here.
9. **The macOS/Windows rfd glue cannot be compiled in situ from Linux** (same pre-existing C-dependency limitation as M1/M1.5: `suramak-core`'s `ring`/rustls and `whisper-rs-sys` need an Apple C toolchain). Mitigation: the *verbatim* glue functions (`pick_audio_file`, `pick_save_dest`) were extracted from the real sources into a throwaway probe crate and type-checked for **both** `aarch64-apple-darwin` and `x86_64-pc-windows-msvc` (exit 0), plus a plain `rfd` probe. The real macOS build + the scripted job run on the macOS CI runner.
10. **Editor dirty tracking compares buffers against the stored segment text**, not against the previous buffer value: the `TextEdit` widget writes into `state.editor.buffers[i]` directly, so an equality check on the incoming text would never mark the editor dirty (found and fixed during the manual UI E2E below; a regression test covers it, and reverting an edit now clears the dirty flag).
11. **The M1 placeholder rows (5 fake recordings) are gone** from the sidebar — the workorder explicitly requires the sidebar to be bound to the real store. When the library is empty the sidebar shows a two-line hint instead. The palette, chrome strip, type scale and panel fractions are unchanged.

## Blockers

1. **The macOS/Windows build of `suramak-ui` (incl. the rfd glue) cannot be compiled from Linux** — pre-existing, documented in M1/M1.5: `suramak-core`'s rustls/`ring` and `whisper-rs-sys` need an Apple C toolchain and there is no osxcross here. Mitigated: verbatim-glue probes type-check on both targets (above), `rfd 0.15.4` checks clean on both targets, and the macOS CI job builds the real bundle and runs the scripted job on Metal/Core ML. **The macOS scripted job has not been executed anywhere in this environment.**
2. **Drag-and-drop (`WindowEvent::DroppedFile`) is wired but not exercised here** — Xvfb offers no drag source to synthesize an XDND drop, and no X automation tool for drags is installed. The handler calls the same `begin_import` entry point that the tested path-field flow uses (unit-tested, incl. validation/failure), and the user smoke on the Mac (workorder: "import a real mp3") will exercise the real drop. Honest status: **wired + code-reviewed, not end-to-end exercised in this environment.**
3. **The in-app debug job takes ~16 s wall under Xvfb/llvmpipe on this 2-core box** (whisper decode + software rendering share the cores; the CLI does the same file in ~4 s). The 120 s watchdog used by the workorder/CI has >7× headroom, but a slower runner would be closer to the limit than the CLI e2e suggests.
