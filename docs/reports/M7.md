## What was implemented

### 1. The pure live module — `crates/suramak-asr/src/live.rs` (NEW, 1126 lines)

Everything except device I/O and the decode thread is **pure values-in/values-out**, compiled on every platform (no `capture` feature needed), so Linux CI unit-tests the whole policy:

- **`LiveScheduler`** — the windowing + backlog state machine. A window closes every `step_ms` (**4 000 ms** default) of new audio and carries `overlap_ms` (**1 500 ms**) of context from the previous window's tail; the first window is clamped at the session start. `push(samples, decoder_busy)` returns the windows ready to decode **now**:
  - every boundary crossed while `decoder_busy` is **skipped** (counted in `skipped_windows()`) and **merged into the next window** — no audio is ever lost from the live transcript, only the cadence degrades;
  - a window's samples cover exactly `[window_start − overlap, boundary)`, so the next decode re-reads the context it needs (the test pins the overlap head byte-for-byte against the previous window's tail).
- **`LiveConfig`** — cadence/overlap/queue bounds enforced (`validate()`): step 4 000–6 000 ms, overlap 1 000–2 000 ms, overlap < step, queue 1–8, 16 kHz stream. Invalid configs are refused by `LiveScheduler::new`/`LiveSession::new`.
- **`LiveWindowQueue`** — bounded FIFO with **drop-oldest** (`push` returns the evicted window; capacity clamps to ≥ 1).
- **`ProvisionalTranscript`** — the merge onto the session timeline: window-relative timestamps are translated via the window's `start_sample`; decoded segments whose end lies within **50 ms** of the covered frontier are the overlap re-decode and are dropped (never duplicated); empty/degenerate segments are dropped; everything else is appended with a fresh `idx` (append-only — the view never reshuffles); `covered_until_ms` and a `revision` counter drive publishing.
- **`LiveSession`** — the glue the runtime drives: `push_audio` → windows; `ingest_decoded` → growing segment list + `skipped_windows()`.
- **`LiveDecoder`** — the (impure) decode thread (`suramak-live-decode`): windows in via a bounded drop-oldest queue (Mutex+Condvar), results out; one window decoded at a time through the **existing whisper machinery** (`whisper::transcribe` + `ContextCache`, same model / language / initial prompt / engine plan, `default_threads`), context loaded lazily on the first window. `is_decoding()` is the backlog guard's input. `Drop` signals shutdown and **detaches** (an in-flight window finishes and the thread exits on its own) — Stop never blocks the UI thread.

### 2. Capture feed — `crates/suramak-asr/src/capture.rs` (additive only)

`MultiRecorder::take_live_chunk()` returns each source's **new** mono samples (device rate) since the previous call via per-source read cursors. Read-only: the accumulated buffers — and therefore the final WAV — are untouched. The no-capture stub carries the same method (empty). One constructor line and one new method; nothing else changed.

### 3. Runtime wiring — `crates/suramak-ui/src/runtime.rs` (purely additive)

- `start_capture` arms the machinery best-effort after the session opens (`start_live`: pure session + decode thread; a missing model / bad config only logs — a recording without live partials is still a working recording).
- `live_tick` (called per frame from `main.rs` while recording, next to the meter sample): drains finished decodes into the provisional transcript → accumulates per-source new samples → flushes **every ≥ 1 s per source, all sources together** through the **same `mix::mix`** engine the final pass uses (per-source gain/mute from the record view; chunk-wise and session-less, i.e. **no drift correction on the live stream** — provisional only) → `scheduler.push_audio(mixed, decoder.is_decoding())` → `decoder.submit(window)` → publishes to the record view when the revision changed.
- `stop_capture` tears the machinery down **first** (decoder signalled + detached); the mix → WAV → `SubmitJob` path is byte-for-byte the M6 code.

### 4. UI — `crates/suramak-ui/src/app/mod.rs` + `app/record.rs`

- `Recording` gains `provisional: Vec<Segment>` + `provisional_skipped: u64`; `record_provisional()` grows them (ignored once stopping); **`stop_recording()` clears them immediately** — provisional content is always discarded on Stop, and the unchanged `StopCapture` → `on_recording_stopped` → `SubmitJob` flow takes over.
- The record view grows a **live transcript card**: the clear label `live transcript — provisional · the final pass runs on Stop`, a `stick_to_bottom` auto-scrolling list of the provisional segments, and the subtle backlog note `N window(s) skipped to keep up — live updates may lag; the final pass is unaffected` when the guard fired. Too-small windows skip the card gracefully; the rest of the view is unchanged.

## Deviations from the WORKORDER (with reasons)

1. **The live decode thread owns its own `ContextCache`** (a second whisper context lives only while the recording runs; dropped at Stop). This keeps `worker.rs` / `pipeline.rs` / `whisper.rs` at **zero diffs** — the structural half of the byte-identical guarantee — at the cost of one extra model load during recording (tiny ~0.2 s; a big model adds its memory for the session's duration, documented in PLAN-NOTES). Reusing the worker's cache would have reshaped `Job`/`WorkerEvent` (the CLI uses both) — a far larger blast radius for the same provisional result.
2. **The live stream is mixed chunk-wise and without clock-drift correction** (`mix::mix(tracks, None)` per ~1 s flush): the drift measurement needs the whole-session span, which does not exist during capture. Provisional only — the final recording is still the one full-session drift-corrected mix; for a single source the live stream is exactly `resample_16k` (the pre-M6 solo path), as the workorder asks.
3. **The provisional merge is drop-only-covered (append-only)**: segments fully inside the already-covered range are dropped; a phrase spoken *across* a window boundary can therefore briefly appear twice (whisper re-decodes it with more context and may re-segment it). The alternative (replacing the previous tail) can silently *lose* words, which is worse for a provisional view; the final pass replaces the whole list, so this can never reach a saved transcript (documented in the module docs and PLAN-NOTES).
4. **The last `< step_ms` of audio is not decoded live** (no flush at Stop): the final pass owns the tail, and a Stop-time live window would only add latency before the final pass it cannot influence.
5. **`suramak-core`'s `Segment` gained `#[derive(PartialEq)]`** (additive): `Recording` derives `PartialEq` and now holds `Vec<Segment>`; the e2e's byte-identity comparison also uses it.
6. **The E2E's simulated decoder is synchronous** (never busy), so every window decodes and the provisional list shows the fast-machine behaviour; the skip-and-merge path is pinned by the pure unit test with exact numbers instead of in the model e2e (the model e2e's job is the words + the byte-identity pin).
7. **Multi-source live mixing is exercised through the pure engine and the runtime code path, not with real devices** — Linux has capture OFF (unchanged). The Mac-only feel is USER_SMOKE item 18.
8. **`stop_recording()` clears the provisional list immediately** (not at wav-write time) — the strict reading of “provisional content is ALWAYS discarded on Stop”; the record view shows the card with a `finishing…` hint for the brief finalising moment.

## Blockers (honest status)

1. **macOS is not available here** — the real feel (words appearing while speaking, the decoder keeping up with a live mic, Core ML/Metal timing, the card's scrolling) can only be exercised on a Mac: **USER_SMOKE item 18** covers it. Everything below the device boundary is verified on Linux: the pure scheduler/queue/merge (8 unit tests with exact numbers), the UI state machine (2 tests), the runtime wiring compiles on the capture build, and the model e2e proves the live scheduler + the real whisper path + the byte-identical final pass.
2. **Two whisper contexts during a recording** (the worker's cache + the live decoder's) is the documented cost of keeping the final pipeline at zero diffs; the live context is dropped at Stop. On very small machines a big model could make this noticeable — the live machinery is best-effort by design (a missing model or a failed decode logs and disables live; the recording and the final pass are unaffected).
3. **Live-update latency is bounded by design, not measured on a Mac yet**: first words after ~4 s (cadence) + model load; updates every ≤ ~1 s (flush) + decode time; a slower machine skips windows (counted) instead of lagging unboundedly.
