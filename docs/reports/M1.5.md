## Deviations from the WORKORDER (with reasons)

1. **Encoder directory naming follows whisper.cpp, not the literal `<model-stem>-encoder.mlmodelc`.** whisper-rs-sys 0.15.0 vendors whisper.cpp whose `whisper_get_coreml_path_encoder()` *strips a trailing `-qX_X`* before appending `-encoder.mlmodelc`; `ggml-large-v3-turbo-q5_0.bin` therefore pairs with `ggml-large-v3-turbo-encoder.mlmodelc`, and all three turbo decoders share one package. Implementing the literal wording would have produced a directory whisper.cpp never looks for. `models::encoder_dir_name()` mirrors the C function and is unit-tested; the zip's own top-level directory is stripped so the destination name stays under our control.
2. **Encoder entries for the models we ship, not for `medium`/`large-v3`.** The workorder lists "tiny, base, small, medium, large-v3, large-v3-turbo"; our manifest (M0 scope) contains no `ggml-medium.bin` / `ggml-large-v3.bin`, so pinning their encoders would be unused bytes in the manifest. Every model we *do* ship has its official encoder pinned (6/6, sharing 4 packages).
3. **`EngineSetting` serde uses explicit `rename`s.** `#[serde(rename_all = "snake_case")]` renders `CoreML` as `core_m_l` (caught by the roundtrip test); explicit `auto|coreml|metal|cpu` renames match the CLI flags and the settings file.
4. **Core ML "compiled" is detected from the linked library, not `cfg!(feature = "coreml")`.** The macOS build enables Core ML through the target-specific `whisper-rs` dependency, so the asr crate's own `coreml` feature would be *off* in exactly the build that has Core ML. `whisper::coreml_compiled()` reads whisper.cpp's `whisper_print_system_info()` (`COREML = 1`), which is also what `doctor` prints.
5. **Core ML engagement is detected from whisper.cpp's own log lines** (success/failure), because whisper-rs exposes no API for it and `whisper_encode_external` is internal. The probe wraps *state* initialisation (where whisper.cpp loads the encoder) and is exercised by a unit test; if no failure is reported and the package existed, Core ML is in use by construction (whisper.cpp only skips it when `whisper_coreml_init` returns null).
6. **`--engine metal|cpu` hides the encoder directory during state init.** whisper.cpp has no runtime Core ML switch (compile-time feature + "directory exists" ⇒ Core ML is used). Without this, `--engine cpu` would silently run the ANE encoder and the reported engine would be a lie. Stash/restore is exercised by unit tests (including the error path) and the directory is restored in all cases; the state keeps the ggml encoder for the whole decode.
7. **Explicit `coreml`/`metal` on a platform/build that cannot honour it downgrades with a warning instead of failing** ("never a hard failure", ENGINES.md), and `engine_used` always reports what actually ran. `Auto` never warns — picking what the machine can do *is* the rule.
8. **`zip` feature selection.** `default-features = false, features = ["deflate-flate2-zlib-rs"]`. The documented `deflate` feature also pulls `zopfli` (compression, unused), and plain `deflate-flate2` fails to compile because flate2 then has no backend selected (`compile_error!("You need to choose a zlib backend")` — hit and fixed during development). `zlib-rs` is pure Rust (no build script, no C files); the encoder packages are deflate-compressed (verified with `zipfile`), which is all we read. New packages in `Cargo.lock`: **`zip 7.2.0`** and its pure-Rust helper **`typed-path 0.12.3`** — no new `*-sys` crate, no new C dependency (`flate2`, `crc32fast`, `miniz_oxide`, `zlib-rs` were already in the lock). `zip` is pinned at 7.x because 9.x requires rustc ≥ 1.88 while the workspace declares `rust-version = 1.85`.
9. **`WorkerEvent::Finished` gained `engine_used` + `warnings`** (and `Job` gained `engine`). No other crate consumes the enum today (`suramak-ui` does not depend on `suramak-asr` yet — verified), so no call site outside `asr`/`cli` needed reshaping.
10. **CI: the two literal `cargo check -p suramak-asr --target aarch64-apple-darwin` steps are not in the linux job** — they cannot pass on a Linux runner: `suramak-asr`'s dependency tree contains C code that needs an Apple toolchain (`ring` via rustls fails first: `cc: error: unrecognized command-line option '-arch'`; `whisper-rs-sys` needs the same class of toolchain), and no osxcross is available. This is pre-existing (same class as M1's note) and not caused by M1.5. Instead the linux job verifies the **feature wiring** with `cargo tree -e features --target aarch64-apple-darwin` (passes on Linux, see acceptance #4) and the **macOS job** builds the darwin target with `coreml` and now runs the encoder download + the Core ML e2e. The macOS-only code path in this milestone is the whisper.cpp/ObjC++ side, which only a Mac can compile.
11. **`models remove` keeps a shared encoder package while another installed turbo decoder still needs it** (otherwise removing `turbo-q5-0` would silently break `turbo`). Verified below.
12. **`models download --encoder` deletes the archive after extraction** (the turbo package is >1 GB); re-running is a no-op because the extracted directory is checked for completeness.

## Blockers

1. **The two `cargo check -p suramak-asr … --target aarch64-apple-darwin` acceptance commands cannot pass from Linux** (pre-existing C-dependency limitation: `ring`/rustls and `whisper-rs-sys` need an Apple C toolchain; no osxcross on this box, and installing one is out of scope/permission). Mitigated as described in deviation 10 — feature wiring verified on Linux, real darwin build + Core ML run on the macOS CI job and the manual check in `docs/ENGINES.md`. **Not a code defect; not fixable inside this milestone.**
2. **Real ANE execution and the "~2–3×" speed claim are macOS-only** — from Linux the download/verify/extract path is fully verified (acceptance #5), but *whether whisper.cpp engages Core ML on a given Mac* is asserted only by `e2e_coreml_encoder_engaged_macos` on macOS. It runs in the macOS CI job; it has **not** been executed anywhere in this environment. The speed class is not re-measured.
