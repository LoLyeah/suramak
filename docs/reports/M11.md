### 2. Request builder — the exact shapes (WORKORDER §2)

`suramak-core/src/polish.rs` now exposes `build_body(segments, cfg, audio)`
where `audio: Option<&AudioChunk>`:

**Text-only (`None`) — byte-identical to the pre-M11 request** (pinned by test
at the builder level *and* on the wire — the mock records the raw request body
and compares it to the pre-M11 `json!` literal):

```json
{
  "messages": [
    { "content": "<SYSTEM_PROMPT>", "role": "system" },
    { "content": "{\"segments\":[{\"id\":0,\"text\":\"…\"}]}", "role": "user" }
  ],
  "model": "<model>",
  "temperature": 0
}
```

**Audio-aware (one request per chunk)** — the user message's content becomes an
array: the same text payload as a `text` part, plus the chunk as an
OpenAI-compatible `input_audio` part:

```json
{
  "messages": [
    { "content": "<SYSTEM_PROMPT>", "role": "system" },
    { "content": [
        { "text": "{\"segments\":[{\"id\":0,\"text\":\"…\"}]}", "type": "text" },
        { "input_audio": { "data": "<base64 WAV>", "format": "wav" }, "type": "input_audio" }
    ], "role": "user" }
  ],
  "model": "<model>",
  "temperature": 0
}
```

The `input_audio.data` is the **complete WAV file** for the chunk (canonical
header + raw PCM16), base64'd **as-is** — the app's 16 kHz mono PCM16
recordings need **no encoder**. `format` is `"wav"`.

(Both blocks are shown grouped for readability; the actual serialization is
`serde_json`'s own key order — the tests pin the **serialized bytes**, not this
layout.)

### 3. The chunker — segment-aligned, ≤ 4 MB raw, full coverage

`chunk_wav(wav, segments, cap)` (`AUDIO_CHUNK_CAP_BYTES = 4 MB` for the
client; the cap is a parameter so tests can pin behavior with small files):

- Cut points are the segments' **start times** (ms → frame-aligned sample
  offsets, rate-honoring).
- Greedy: a chunk ends at the **latest cut that keeps it within the cap**, so a
  segment is never split mid-segment when a boundary allows it. A single
  segment longer than the cap is split at the cap — the only forced
  mid-segment cut (documented; a chunk that would then carry no segment start
  is skipped at request time rather than sent with an empty payload).
- Every sample of the recording appears in **exactly one chunk, in order** —
  the tests decode each chunk's WAV back and assert the concatenation equals
  the original PCM byte-for-byte, and that each chunk is within the cap.
- One request per chunk; the corrected outputs are **concatenated in order**
  (each chunk's reply is validated against that chunk's segment subset, then
  the concatenation is re-checked against the full segment list).

### 4. The graceful ladder (WORKORDER §3) — degrade, never fail hard

Resolution happens in the UI (`polish_audio_request`, egui-free + tested):

| State | What happens |
|---|---|
| Toggle **off** | `AudioRequest::Off` — today's exact request, no notes |
| Toggle on, **no audio attached** | text-only + note (`…no audio is attached to this transcript…`) |
| Toggle on, **file gone** (keep-audio off / moved import) | text-only + note (`…keep audio was off, or the file is gone…`) |
| Toggle on, **recording there** | read → parse; a 16 kHz mono PCM16 WAV goes as-is; anything else (imported mp3/mp4, another WAV shape) is decoded + resampled through the pipeline's own `decode`/`resample` path |
| Read/decode/resample fails | text-only + note naming the reason (`could not read the recording: …`) |
| Recording holds no audio | text-only + note (`it holds no audio`) |
| Endpoint **4xx** on an audio request | **one automatic text-only retry** for the whole transcript + note naming the status and the endpoint's message (`the endpoint rejected the recording (HTTP 400: …) — retried without it`) |
| Endpoint 5xx / transport error | the run fails exactly like today (raw error; the M4 no-partial-apply rule — pinned by a test) |
| Reply fails validation | the run fails exactly like today |

Notes surface in the **polish line with the review** (the editor's polish bar) —
the same surface that shows today's polish messages (`PolishReview.notes`, joined
with ` · ` onto the review caption).

## Deviations (with whys)

1. **One request per chunk** (not one request carrying all chunks as several
   `input_audio` parts). "Corrected outputs concatenated in order" only means
   something with per-chunk requests, and chunking exists to bound the request
   size — putting every chunk in one request would defeat that. It is also the
   shape OpenAI-compatible servers actually accept (one audio part per
   message). The workorder's "`input_audio` part(s)" is honored: a request
   carries the part(s) of its chunk (exactly one).
2. **Imported files are decoded + resampled** through the pipeline's own
   `decode`/`resample` when the bytes are not already 16 kHz mono PCM16 —
   `audio_path` for an imported file is the *original* file (mp3/mp4/webm…),
   and the task brief calls out "/ a file is attached" as a case where a
   recording exists. The recording case itself needs **no encoder** (asserted:
   the chunk is the file's exact bytes).
3. **The 4xx-only retry trigger** is exactly as specified; 5xx/transport
   failures keep the M4 fail-the-whole-run semantics (no partial apply). Pinned
   by a test so a future "helpful" widening is a deliberate decision.
4. **The settings key name** is `settings.polish.send_audio` (the workorder
   named the toggle's copy, not the key).
5. **`base64` added as a direct workspace dependency** (0.22 — already in
   `Cargo.lock` via reqwest's transitive graph; nothing new is downloaded).
   `base64` + `serde_json` were added to `suramak-ui`'s
   `[dev-dependencies]` so the UI tests can decode/parse what goes on the wire.
6. **The CLI `polish` command stays text-only** (`send_audio: false`): M11 is
   an in-app Settings option per the workorder (Settings toggle + in-app review
   UX). Extending the CLI later is a two-line change; recorded as a boundary.
7. **A chunk that would carry no segment start is skipped** (no empty
   payloads): only reachable when a single segment alone exceeds the 4 MB cap
   (the forced mid-segment split). The chunker itself still tiles every sample.
8. **Notes ride the review line**, not the app status line — "exactly like
   today's polish warnings" means the surface the polish flow already uses for
   its messages.
9. **Memory**: the recording is read and parsed whole before chunking
   (16 kHz mono PCM16 ≈ 32 KB/s → a 2 h recording ≈ 230 MB on disk, a few
   hundred MB peak while chunking). Fine for the app's recordings; streaming
   chunk construction is a documented future option, not needed now.

## Honest boundaries

- **Real-endpoint e2e = the owner with their key.** No real endpoint was
  contacted by any test or by this executor; the mock server is the only
  network path exercised. USER_SMOKE §31 is the owner's checklist (toggle on →
  polish an English clip against their endpoint → confirm the audio-aware run or
  the fallback note; confirm OFF is unchanged).
- **Chunking over 4 MB** was exercised with a synthetic 140 s / 4.48 MB WAV
  against the mock (2 requests, full coverage) and with small caps over small
  files; no real 2-minute-plus recording was sent to a real endpoint.
- **macOS/Windows runtime unverified** (Linux VPS only): the new Settings row is
  compile-checked and reuses the existing row/caption primitives (M9e wrapping),
  but its look is owner-smoke territory.
- **The CLI polish command is text-only** (deviation 6).
- **Memory**: whole-recording read + parse before chunking (deviation 9).
- **The client's 120 s per-request timeout is unchanged** (the M4 setting). A
  slow audio model chewing a full 4 MB chunk could approach it; if the owner's
  endpoint hits it, the run fails with the raw timeout error like any other
  transport failure — worth a Report note in §31.
